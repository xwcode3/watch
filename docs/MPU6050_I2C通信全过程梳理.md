# MPU6050 启动过程 I2C 通信全过程梳理

> 依据：`2026-10-17` 的 APP 启动日志 + `Core/Src/iic.c`、`BSP/MPU6050/bsp_mpu6050_driver.c`、
> `BSP/MPU6050/bsp_mpu6050_handler.c`、`Core/Src/FreeRTOS_tasks.c` 源码逐行对照。
> 结论：这段日志里 **I2C2 总线上一共发生 19 次事务**（16 次写、2 次单字节读、1 次 14 字节 DMA 读），
> **第 19 次写失败**，之后总线上再没有任何通信。

因为此刻 INT_EN 只有 0x10 这一位。

## 3. 三种帧在总线上的字节

### ① 写一个字节（16 帧）
```
S | 0xD0 | A | reg | A | data | A | P
```
对应 `mpu_write_reg()`：等 BUSY=0 → START（EV5）→ 地址+W（EV6）→ 寄存器地址（EV8_2）→ 数据（EV8_2）→ STOP。

### ② 读一个字节（第 8、17 帧）
```
S | 0xD0 | A | reg | A | Sr | 0xD1 | A | data | N | P
```
对应 `mpu_read_reg()`：第二阶段 **RESTART（不发 STOP）** 后改读方向；
`len==1` 时在等 EV7 之前就先 `I2C_AcknowledgeConfig(DISABLE)` + `I2C_GenerateSTOP`，
主机回 NACK 让从机停止输出，再读 DR。

### ③ DMA 连续读 14 字节（第 18 帧）
```
S | 0xD0 | A | 0x3B | A | Sr | 0xD1 | A | b0..b13 | N | P
```
- 前 13 个字节由 DMA 自动回 ACK；
- 最后一个字节的 **NACK + STOP 不是软件发的**，是 `I2C_DMALastTransferCmd(I2C2, ENABLE)`（置 CR2.LAST）后由硬件在最后一个 DMA 请求结束时自动产生；
- 收完 → DMA1_Stream2 TC 中断 → `pf_dma_interrupt_callback`。

## 4. 时间账（100 kHz，1 bit = 10 µs）

| 帧类型 | 位数 | 估算耗时 |
|---|---|---|
| 写 1 字节（3 字节 + START/STOP） | ≈29 bit | 0.3 ms |
| 读 1 字节（试 5 字节） | ≈47 bit | 0.5 ms |
| DMA 读 14 字节（试 18 字节） | ≈162 bit | **1.7 ms** |

- 初始化 15 帧 ≈ 14×0.3 + 0.5 ≈ **4.7 ms 总线时间**，加上 `delay_ms(100)` + `delay_ms(10)` ≈ **115 ms**。
- 中断路径 4 帧 ≈ 0.3 + 0.5 + 1.7 + 0.3 ≈ **2.8 ms 总线时间**。

### 为什么 `get timestamp start` 与 `get timestamp end` 都是 2436？
不是取样过快，而是 **SysTick 被饿死**：SysTick / PendSV 优先级是最低档（`configKERNEL_INTERRUPT_PRIORITY = 15`），
而 EXTI9_5 和 DMA1_Stream2 都是 5，无法被 SysTick 抢占。
`DEBUG_OUT` = `printf`，USART1 115200、忙等发送，**一行 35~49 字符约 3~4 ms**；
`int_interrupt_callback` 里夹着 5~6 条打印，整个 ISR 就有 **20 ms 量级**，这段时间 `xTaskGetTickCount()` 根本不走。
所以两个时间戳必然相等 —— 这两个时间戳目前**不能用来测 DMA 耗时**。

## 5. 第 19 帧为什么失败

`iic_mem_write()` 把 `mpu_write_reg()` 的返回值映射成 `0 → 1`、非 0 → `-1`，
所以日志里的 `ret = -1` 只能说明：`mpu_write_reg()` 在下面 5 个等待点之一超时/异常，**具体是哪一个没有留下来**：

| 序号 | 失败点 | 现象 |
|---|---|---|
| a | `i2c_wait_idle()` 等 BUSY=0 超时 | 上一帧（DMA 读）的 STOP 没真正收尾 |
| b | EV5 `MASTER_MODE_SELECT` 超时 | START 没发出去（总线被拉住） |
| c | EV6 `TRANSMITTER_MODE_SELECTED` 超时 | 0xD0 没被应答（AF） |
| d | EV8_2 `BYTE_TRANSMITTED`（reg）超时 | 从机没吃寄存器地址 |
| e | EV8_2 `BYTE_TRANSMITTED`（data）超时 | 数据字节没发完 |

每条失败路径都会走 `i2c_abort()`：补发 STOP、恢复 ACK，把总线拉回空闲。

### 最可疑的两点（与今日 20:54 复测的判断一致）

1. **DMA 读的终止握手不完整**：`DMA1_Stream2_IRQHandler` 在 TC 里只做了
   `DMA_Cmd(DISABLE)` + `I2C_DMACmd(DISABLE)` + `I2C_AcknowledgeConfig(ENABLE)`，
   既不清 `CR2.LAST`、不等 BTF、不校验 `BUSY`，也不在必要时软件补 STOP。
   对比 HAL 的 `I2C_MasterRxCplt`：停流 → 清 LAST → 关 DMAEN → 关 ACK → 等 BTF → 软件 STOP → 确认 BUSY=0。
   少了这一套，一旦硬件那侧的自动 NACK+STOP 没收干净，`BUSY` 就可能恒为 1，
   于是第 19 帧的第一步 `i2c_wait_idle()` 直接超时 → `-1`。这也解释了为什么**之后永久死**：总线被占死，没有恢复逻辑。
2. **在 ISR 里做阻塞式 I2C 写且无重试**：`dma_interrupt_callback` 直接调用 `mpuxxx_set_interrupt_enable()`（忙等 0.3 ms + 打印）。
   失败一次就再也没有机会，`INT_EN` 永远停在 0x00。

> 备选嫌疑：TC 里 `I2C_AcknowledgeConfig(ENABLE)` 与末字节 ACK 位的竞态（RXNE 之后约 10 µs 内改 ACK，
> 可能把该 NACK 的末字节变成 ACK）。本版 ISR 里夹着 `printf`，实际把这行推后了近 ms，所以嫌疑次之；
> 一旦关掉 ISR 打印，它就会浮上来。无论如何，**TC 回调里都不该碰 ACK** —— `iic_mem_read_dma()` 的请求阶段本来就会重新 ENABLE。

### 直接后果（与日志完全吻合）
第 19 帧失败 → `INT_EN` 保持 **0x00** → INT 引脚不再有任何翻转 → 不再进 EXTI →
`unpack_task` 只处理了第 18 帧那一包（日志里 `UnpackThread az=1.267` 就是这一包）→ **之后彻底静默**。
这也是为什么日志像「跑通一帧就死」。

### 10 分钟定位方法
在 `iic.c::mpu_write_reg()` 的每个 `return -1` 前改成返回不同错误码
（如 `-1/-2/-3/-4/-5`），或在失败时打印 `I2C2->SR1 / I2C2->SR2 / CR2`：

```c
if (i2c_wait_idle() != 0) { log_e("idle BUSY SR2=%04X", I2C2->SR2); i2c_abort(); return -2; }
...
if (i2c_wait_event(I2C_EVENT_MASTER_TRANSMITTER_MODE_SELECTED) != 0U) {
    log_e("addr NACK SR1=%04X SR2=%04X", I2C2->SR1, I2C2->SR2); i2c_abort(); return -4;
}
```
`SR1.AF(bit10)=1` → 地址/数据被 NACK（嫌疑 c/e）；`SR2.BUSY(bit1)=1` 一直不落 → 嫌疑 a。

## 5.1 附：`0x15` 里的 FIFO_OFLOW 是必然，不是偶发

**先算账**：`0x23 = 0x78` 使能了 ACCEL + XG/YG/ZG 四路入 FIFO = **12 B/样本**（`TEMP_FIFO_EN(0x80)` 没开，所以不是 14 B）；
`0x6A = 0x40` 打开 FIFO_EN；ODR = 1000/(1+25) ≈ **38.46 Hz**
→ 写入速率 12 × 38.46 ≈ **461 B/s**，1024 B ÷ 461 B/s ≈ **2.22 s**。
日志首次中断 tick = 2436 ms，扣掉 init 之前的约 200 ms 正好 2.2 s —— 这条中断就是算出来的溢出点。

**根因就一句：FIFO 开了，但从来没有被读过。** 中断里 `iic_mem_read_dma(0x3B, 14)` 读的是
**传感器寄存器组（0x3B–0x48）**，不是 `FIFO_RW(0x74)`；FIFO_COUNT 也从未被读。FIFO 实际只被当成一个
"2.2 秒定时器"在用，里面 85 包数据全部作废。

**溢出后硬件变成什么样**（RM-MPU-6000A-00 §4.31 原文）：
> "When the FIFO buffer has overflowed, the oldest data will be lost and new data will be written to the FIFO."

- 滚动覆盖最旧字节，且 `FIFO_COUNT` **饱和在 1024**，无法得知丢了多少；
- 覆盖是按字节滚的，**包边界会错位**：之后直接读 `FIFO_RW` 拿到的 12 字节组不再对齐，
  必须 `FIFO_RESET`（0x6A bit2）才能恢复；
- 也就是说溢出之后 FIFO 由"可用"变成"必须先 reset 才可用"，而代码里没有任何 reset。

**危害分层**：
1. 功能上暂时无害 —— 0x3B 寄存器影子一直在更新，读到的仍是最新样本，所以数据看着是对的（别把这点当成 FIFO 在工作）。
2. 时序上是错的 —— 溢出周期 = 1024 ÷ 12 ÷ ODR，一改量程、ODR、入 FIFO 的通道就漂移，2.2 s 是巧合不是设计。
3. 排障/扩展有雷 —— FIFO 永远停在满状态，`INT_STATUS.bit4` 会一直是 1；若把 INT_EN 常开且顺手使能了
   FIFO_OFLOW，就会变成中断风暴。

**两条改法（选一条）**：
- **A 不用 FIFO（推荐）**：`0x23 ← 0x00`、`0x6A` 清 FIFO_EN，INT_EN 只留 `DATA_RDY(0x01)`，
  中断里照旧读 0x3B 的 14 字节。38.5 Hz、每 26 ms 一次，负载很低。
- **B 真用 FIFO**：中断里先读 `FIFO_COUNT_H(0x72)` 再读 `FIFO_COUNT_L(0x73)`（顺序不能反），
  取 `count / 12` 个整包 burst 读 `0x74`，余数字节丢弃；**只有检出 overflow 时才 FIFO_RESET**（此时包边界已断）。
  好处是 2.2 s 的 85 包一次取完、零丢样。

**为什么不能"把 FIFO 当节拍源"**：`FIFO_OFLOW` 是"缓冲满了"的告警，不是周期信号。
FIFO 满之后停在满状态（滚动覆盖），要拿到下一个"2.2 s 节拍"必须先 `FIFO_RESET` 把指针清回 0；
不 reset 的话，读走 INT_STATUS 后它要么随每次写入反复置位（≈26 ms 一次的风暴），要么从此安静 ——
两种都不是"每 2.2 s 一帧"。节拍源应该是 `DATA_RDY`（每样本一次），FIFO 要么彻底不用、要么按整包消费。

> 当前日志里"只触发一次"是第 19 帧失败后 `INT_EN=0x00` 造成的**假象**，不是设计目标。

## 6. 顺带发现的与日志不符之处

| 位置 | 问题 |
|---|---|
| `mpuxxx_init` 采样率 | 写的是 `SMPLRT_DIV = 0x19`(25)，DLPF 使能后 gyro 输出 1 kHz，实际 ODR = 1000/26 ≈ **38.5 Hz**，日志却打印 "50Hz"（注释里想写的是十进制 19） |
| `mpuxxx_init` DLPF | `0x04` 对应加速度 21 Hz / 陀螺 20 Hz，日志打印 "25Hz" |
| `mpuxxx_init` | `DATA_RDY_EN` 写成功，紧接着的 `log_i` 却写 "interrupt disable success"，语义反了，排障时极易误导 |
| `mpuxxx_fifo_init` | 最后开的是 FIFO 溢出中断，`dma_interrupt_callback` 里重开的却是 DATA_RDY，两者不对称 |
| 数据通路 | FIFO 一直在灌（`0x23=0x78`），但中断里**读的是 0x3B 起的寄存器组，不是 FIFO**，FIFO 只起到"定时器"的作用，且每次都在溢出 |

| 中断上下文 | ISR 里 `printf`（115200 忙等）单行 3~4 ms，直接把 tick 冻住，实时性完全丧失 |

## 7. 建议的最小改动顺序

1. **ISR 去 printf**：`DEBUG_OUT` 在 ISR 路径上改为置标志、由任务打印，或整体关掉。
2. **0x38 重开移出 ISR**：`dma_interrupt_callback` 只置标志/发通知，由 `unpack_task` 完成"重开中断"这次写，并**允许重试 2~3 次**。
3. **错误码分级**：`mpu_write_reg` 返回具体失败环节，别再统一 `-1`。
4. **TC 回调别动 ACK**：删除 `I2C_AcknowledgeConfig(I2C2, ENABLE)`，需要时先等 BUSY=0。
5. 想真正用满 38.5 Hz：把中断改成 `DATA_RDY_EN`，去掉 FIFO；要用 FIFO 就按 `FIFO_COUNT + FIFO_RW` 一次取多包。

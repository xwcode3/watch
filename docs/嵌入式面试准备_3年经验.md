# 嵌入式软件工程师（3 年经验）面试准备文档

## 一、MCU / 时钟 / 启动

### Q1. STM32F411 上电到 main 之前发生了什么？你的工程里 App 的 VTOR 为什么设成 0x08010000？
**答**：上电后硬件从 `0x08000000` 取 MSP 初始值、从 `+4` 取复位向量；进 `Reset_Handler`→`SystemInit`→`__main`（C 库拷贝 `.data`、清零 `.bss`）→`main`。本工程是 **App（非 Bootloader）**，所以 `app_pre()` 里 `SCB->VTOR = FLASH_BASE | 0x10000`，把中断向量表重定位到 `0x08010000`，因为 App 的向量表被链接器放在那里（见 `STM32F411XX_FLASH.ld`：`FLASH ORIGIN=0x08010000`）。若不设 VTOR，中断会跳到 Bootloader 的向量表，导致 HardFault 或错乱。
**追问**：VTOR 有哪些对齐要求？（必须 2^n 对齐，且 ≥ 向量表大小；0x08010000 满足。）Bootloader 跳转 App 前要做哪些对称动作？（关自己的中断/外设、清 RCC、`__set_MSP(app_sp)`、`SCB->VTOR=app_base`、跳复位向量——见 `boot_manager.c::JumpToApp1`。）

### Q2. 你的 100MHz 系统时钟是怎么配出来的？Flash 等待周期为什么要配 3？
**答**：`SystemClock_Config()` 用 HSE=25MHz 作 PLL 源：`RCC_PLLConfig(HSE, PLLM=12, PLLN=96, PLLP=2, PLLQ=4)` → VCO=25/12×96=200MHz，SYSCLK=200/2=**100MHz**；PCLK1=HCLK/2=50MHz（APB1 上限 50M），PCLK2=100MHz。Flash 等待周期 `FLASH_Latency_3`：F411 在 100MHz 需要 3 个 wait state（参考 datasheet 的"编号 vs 频率"表），配少了会取指错、配多了降性能。`FLASH_PrefetchBuffer/InstructionCache/DataCache` 一并开启。
**追问**：PLLQ=4 给谁用？（USB OTG FS，48MHz 左右；本工程未用 USB。）为什么要先 `PWR_CR_VOS` 设 Scale1 再升频？（F411 跑 100MHz 必须电压调节器 Scale1。）

### Q3. `SysTick_Config(SystemCoreClock/1000)` 的 1ms 是怎么来的？FreeRTOS 的 tick 与之什么关系？
**答**：SysTick 每 `SystemCoreClock/1000` 个周期减到 0 触发一次，即 100MHz/1000=100000 周期=1ms 一次中断。`configTICK_RATE_HZ=1000` 让 FreeRTOS 以 1ms 为时基，`vTaskDelay(2000)`=2s。SysTick 中断里 FreeRTOS 做任务调度记账。
**追问**：把 tick 改成 100Hz 有什么利弊？（功耗更低、上下文切换更少，但时间分辨率变粗，`vTaskDelay(1)` 会变 10ms。）

## 二、Bootloader / OTA 架构

### Q4. 画一下你们 OTA 的整体流程，App 和 Bootloader 的职责怎么划分？
**答**：
- **App 侧（`ota_task`）**：等命令 `11 22 33` → 进 `OtaDownload` → `Ymodem_Receive_2buffer` 把**密文固件**收进 **W25Q64 外部 Flash**，同时把状态 `0x22` 和固件长度写 **AT24C02 EEPROM** → 等 `55 66 77` → 按键确认 `SoftReset()`。
- **Bootloader 侧（`boot_manager.c`）**：上电读 EEPROM 状态；若需要更新，从 W25Q64 读出密文、用 `Aes_IV_key256bit_Decode`（AES-256-CBC）**解密**后写内部 Flash（`copy_app_to_executable`），校验后 `JumpToApp1()` 跳转。
- 两者通过 **EEPROM 里的 OTA 状态字** 作为契约通信。
**追问**：为什么升级包先落外部 Flash 而不是直接写内部 Flash？（掉电可恢复、内部 Flash 写时不能跑在自身 Flash 上、外部 Flash 容量大可做双备份。）

### Q5. 你们 OTA 状态机有哪些状态？App 上电为什么要"自检 OTA 状态字"？
**答**：状态字存在 EEPROM 0x00：`0x00 NO_APP_UPDATE / 0x11 DOWNLOADING / 0x22 DONE / 0x33 FIRST_CHECK_START / 0x44 FIRST_CHECKING / 0x55 NEED_UPDATE`。App `main()` 启动后读它：若 `==0x44` 说明 Bootloader 刚升级完在等 App 确认，App 写回 `0x00` 并 `while(1)` 让 Bootloader 的看门狗复位；若 `!=0x00` 且不是正常态，则 `SoftReset()` 交还 Bootloader。这样保证"半途而废的升级"不会让 App 带着错误状态直接跑起来。
**追问**：如果升级中途断电，重启后会怎样？（EEPROM 停在 `0x11/0x22`，App 自检发现 ≠0x00 → SoftReset → Bootloader 据此决定重下或回滚。需要 Bootloader 配合实现。）

### Q6. `SoftReset()` 为什么用 `__set_FAULTMASK(1)` 再 `NVIC_SystemReset()`？
**答**：`__set_FAULTMASK(1)` 屏蔽所有可屏蔽+HardFault 以外的中断，防止复位过程中被中断打断导致状态不一致；`NVIC_SystemReset()` 是内核标准复位（比单纯置 PC=0 更干净，会复位外设与内核）。
**追问**：和"跳转函数里 `__disable_irq()`"有何区别？（`__disable_irq` 只是 PRIMASK，FaultMask 还能挡 HardFault；复位场景用 FaultMask 更彻底。）

## 三、FreeRTOS 深入

### Q7. 你的工程用了抢占式调度，讲讲任务切换的时机与你们的优先级设计。
**答**：`configUSE_PREEMPTION=1`，时间片 1ms。切换发生在：① 高优先级任务就绪（ISR 释放资源/`xTaskNotifyFromISR`）；② 当前任务阻塞（`vTaskDelay`/队列/信号量）；③ 时间片到（同优先级）。本工程任务：`led_blink_task`(prio1)、`ota_task`(prio2)，idle/timer 在更低优先级。`configMAX_PRIORITIES=5`。
**追问**：为什么 OTA 任务优先级比 LED 高？（OTA 要即时响应命令、下载是业务主路径；LED 只是心跳，可被打断。）优先级设太高（比如 0）会怎样？（可能饿死内核服务；且 0 通常留给看门狗/极关键 ISR。）

### Q8. 队列、信号量、任务通知（Task Notification）在你项目里分别用在哪里？各自适用场景？
**答**：
- **队列 `Q_YmodemReclength`**：USART1 IDLE 中断 `xQueueSendFromISR` 把"收到长度"发给 `ota_task` 阻塞接收——适合**传数据/单生产者单消费者**。
- **任务通知 `xTaskNotifyFromISR/xTaskNotifyWait`**：在 ADC/DMA 框架（`FreeRTOS_tasks.c`，虽未启用）里 DMA 完成中断通知任务——**轻量、零拷贝、一对一**，比队列/信号量省 RAM 与 CPU。
- **互斥锁 `g_xMutex`**：保护 ADC 采样数据临界区，且带**优先级继承**（防优先级反转）。
**追问**：任务通知相比二值信号量快多少、限制是什么？（快、省，但只能一对一，不能多消费者/不能用于中断间同步。）

### Q9. `configMAX_SYSCALL_INTERRUPT_PRIORITY=5` 到底在限制什么？你们的 USART1 中断优先级设 5 合规吗？
**答**：这是"**能安全调用 FreeRTOS FromISR API 的最高（数值最小）中断优先级**"。数值 ≤5 的 ISR 可以调 `...FromISR`；>5 的 ISR **绝不能**调（会破坏内核临界区）。USART1 设成抢占优先级 5，刚好在阈值上，合规；但代码注释要求 DMA 半/全满中断优先级"要比 IDLE 高（数值更小）"，否则 DMA 抢在 IDLE 前处理会乱序——这是本项目特意做的优先级编排。
**追问**：如果某个优先级 3 的 ISR 里误调了 `xQueueSend`（非 FromISR 版）会怎样？（临界区被破坏，可能死锁/HardFault，极难复现。）

### Q10. 你们 FreeRTOS 内存管理用 heap_4，静态/动态分配各有什么取舍？
**答**：`OS/port/heap_4.c` 用**一块大数组 + 最佳适配 + 合并相邻空闲块**，支持 `vPortFree`、适合运行时创建/删除任务。本工程 `configSUPPORT_DYNAMIC_ALLOCATION=1`，任务都用 `xTaskCreate`（动态）。`configTOTAL_HEAP_SIZE=75KB`（128KB RAM 里占 75KB，需注意剩余给 .bss/.data/栈）。
**追问**：heap_4 的缺点？（不防碎片长期累积；无确定性上限。）什么时候该用静态分配 `xTaskCreateStatic`？（安全关键/不允许运行时分配失败，如汽车/医疗。）

### Q11. 栈溢出的风险你们怎么防？`configCHECK_FOR_STACK_OVERFLOW` 当前是 0 有什么后果？
**答**：当前 `=0` 表示**完全不检测**栈溢出。应设 `=2`（每切上下文检查栈尾哨兵字），并实现 `vApplicationStackOverflowHook` 做记录/复位。`uxTaskGetStackHighWaterMark()` 可在运行时打印"历史最小剩余栈"，用来反推安全栈大小。
**追问**：为什么栈溢出很危险却默认关？（检测有少量开销；但生产必须开。本项目 `ota_task` 栈 256 words、内部有 1030B 静态缓冲，栈本身没爆，但 `printf` 深度调用有风险。）

### Q12. `configASSERT` 被定义成死循环，你怎么看？
**答**：`if(x==0){taskDISABLE_INTERRUPTS();for(;;);}`——断言失败直接**关中断死循环**。好处是现场冻结、便于连调试器看调用栈；坏处是产品现场会"假死"。生产可用 `configASSERT` 调一个 `vApplicationAssertHook` 写日志/看门狗，而不是直接锁死。
**追问**：和 HardFault_Handler 里死循环同理，怎么用 RTT/串口把死前信息捞出来？（EasyLogger+RTT，断言前先 `log_e`；或用 `uartx` 输出现场。）

## 四、中断 / DMA / 串口

### Q13. 你们用"DMA + 串口空闲线(IDLE)"收 OTA 命令，讲讲原理和标志清除顺序。
**答**：USART1 开 `USART_IT_IDLE`，DMA2_Stream2 把串口数据搬进命令缓冲（Normal 模式，收 N 字节）。一帧发完总线静默触发 **IDLE**，ISR 里**必须先读 SR 再读 DR 清 IDLE 标志**（`temp=USART1->SR; temp=USART1->DR;`），否则中断反复进。然后 `rec_len = ndtr_init - DMA_GetCurrDataCounter()` 得本帧长度，用 `xQueueSendFromISR` 通知任务，`portYIELD_FROM_ISR` 触发调度。
**追问**：为什么用 IDLE 而不是 RXNE 逐字节？（IDLE 天然分帧，CPU 占用极低；逐字节中断在 115200 下开销大、易丢。）Normal 模式和 Circular 模式在这里怎么选？（命令是定长 4 字节、一次性，用 Normal + 收完重武装 `uartx_receive2idle_dma`；如果是变长流才考虑 Circular+HT/TC 双缓冲。）

### Q14. 进入 Ymodem 下载时为什么要 `YmodemUart_EnterRxMode()` 关掉 DMA 和 IDLE？
**答**：Ymodem 引擎用 `SerialKeyPressed()` **轮询 USART1->DR** 收每个字节（要精确按协议超时/重传）。若不关 DMA，DMA 会和轮询抢同一个 DR；若不关 IDLE，每帧结束会误触发 `Q_YmodemReclength` 命令队列、污染状态机。所以下载前关、下载后 `YmodemUart_RestoreDmaMode()` 再开。
**追问**：轮询收 Ymodem 有什么代价？（占用 ota_task 全程、不能并发处理别的；本项目能接受，因为下载时本就该专注。若想并发应恢复"双缓冲→消费者任务写 Flash"的设计。）

### Q15. DMA 双缓冲/循环模式你在项目里见过，讲讲半传输(HT)和全传输(TC)中断怎么用来"无丢字节"收流？
**答**（结合 `usart.c` 里被 `#ifdef USART1_DMA_RING` 包围的代码）：Circular 模式下一buffer 分两半，DMA 填前半触发 **HT** 中断（CPU 去处理前半），填满触发 **TC**（处理后半），CPU 与 DMA 并行、永不覆盖未处理数据。`dma_half_irq_callback/dma_comp_irq_callback` 就是钩子。本项目 OTA 命令是定长，所以没用这套，但 ADC/DMA 框架（`FreeRTOS_tasks.c`）用 `xTaskNotifyFromISR(DMA TC)` 是同一思路。
**追问**：HT/TC 里能不能做耗时处理？（不能，ISR 要快；耗时处理丢给任务，ISR 只通知。）

### Q16. NVIC 优先级分组在 Cortex-M 上怎么理解？你的工程为什么有的中断设 5、有的设 6？
**答**：Cortex-M 用 **抢占优先级 + 子优先级**；FreeRTOS 一般把分组设成"全部是抢占优先级"（`__NVIC_PRIO_BITS=4`，16 级）。数值越小优先级越高。本项目注释明确要求：DMA 半/全满中断优先级 **必须高于（数值小于）** IDLE 中断，否则 DMA 处理顺序乱；所以 DMA 相关置 5、USART1(IDLE) 置 6。又因 `MAX_SYSCALL=5`，置 5 的 ISR 可安全调 FromISR API，置 6 的也安全（>5 内的都安全）。
**追问**：子优先级在抢占式 RTOS 里还有什么用？（同抢占优先级下决定 ISR 嵌套顺序，但不影响任务调度。）

## 五、存储 / 驱动

### Q17. STM32 内部 Flash 写之前为什么要先擦除？扇区结构怎么算？你们 `flash_erase` 有 bug 吗？
**答**：Flash 只能把 1 写 0，不能把 0 写 1，所以**写前必须整扇区擦除**（全 1）。F411 扇区不等长（前 4×16KB、后 64/128KB…），`STMFLASH_GetFlashSector()` 按地址二分返回扇区宏，`flash_erase` 擦区间所有扇区。**有 bug**：`for(i=0;i<=12;i++)` 访问 `Flash_Sectorsize[12]`，但数组只有 12 项(0~11)，**越界读**属 UB，最坏会误擦扇区。应改 `i<FLASH_SECTOR_NUM`(=12)。
**追问**：擦除最小单位 vs 编程最小单位？（擦除=扇区，编程=字/双字；写前必须 Unlock，写后 Lock。）

### Q18. W25Q64 的"扇区/页"和 STM32 内部 Flash 的"扇区"一样吗？你们的写缓存怎么设计？
**答**：不一样。W25Q64：页 256B（编程单位）、扇区/子扇区 4KB（擦除最小单位）、块 64KB。你们的 `W25Q64_WriteData` 用 4KB `databuf` 做缓冲：攒满一个子扇区才 `Erase_Block + 16×Page_Write`，用 `write_index` 记总字节数，`W25Q64_ReadData` 按 4KB 回读。这样避免每写几字节就擦一次（Flash 擦写寿命有限、且慢）。
**追问**：W25Q64 写之前要 `WriteEnable` 吗？（要，每轮擦除/写前发 WREN 指令，且写状态位要等 WIP 清。）

### Q19. SPI 你配的是 Mode0、预分频 256，速率大概多少？全双工收发的注意点？
**答**：SPI1 在 APB2=100MHz，预分频 256 → ≈**390kHz**（`spi1_init`）。`CPOL=Low/CPHA=1Edge`=Mode0，与 W25Q64 默认兼容。全双工：`spi1_read_write_byte` 先等 TXE 发、再等 RXNE 收，**收发同步进行**——读数据时也要发哑元字节（0xFF）把时钟跑起来。
**追问**：为什么读 SPI Flash 要先发 0xFF 哑元？（全双工总线，主机不发时钟从机就不吐数据；发 0xFF 仅产生 SCK。）速率 390kHz 偏慢，瓶颈在哪、怎么提速？（改 `SPI_BaudRatePrescaler` 到 2/4/8，W25Q64 支持到 80+MHz，注意 PCB 走线与信号质量。）

### Q20. AT24C02 的页写、ACK 轮询你项目里怎么做的？为什么写后要等？
**答**：`ee_WriteBytes` 按 AT24C02 **页大小 8 字节**做页写；跨页要重新发起始+地址；每写完一页 EEPROM 进入内部写周期（≤10ms），代码用 `for(m=0;m<1000;m++){Start;SendAddr;if(WaitAck==0)break;}` 做 **ACK 轮询**等它就绪，而不是瞎延时。读是随机读序列（写地址→重复起始→读数据→末字节 NACK）。
**追问**：I2C 上拉电阻怎么选？（取决于总线电容与速率，一般 4.7kΩ；长线/多从机要算。）

## 六、通信协议 / 安全

### Q21. Ymodem 一帧长啥样？你们的 CRC 用的是什么？
**答**：起始 `SOH`(128B)/`STX`(1K) + 包号 + `~包号`(补码校验) + 数据 + **2 字节 CRC16**。包号与反码不一致直接 NAK；数据 CRC 用 **XMODEM CRC16**（`crc_xmodem`，本项目 `crccitt.c`）。第 0 包是文件名+长度，普通数据包含 `PACKET_HEADER` 偏移。EOT 表示传完，CA 表示中止。
**追问**：为什么用 CRC16 不用校验和？(CRC 能检突发错误，校验和检错弱。）接收端超时/错包怎么处理？（NAK 重传，错误超 `MAX_ERRORS` 发 CA 中止。）

### Q22. 你们固件加密用 AES-256-CBC，讲讲 CBC 模式和你们的实现注意点。
**答**：`Aes_IV_key256bit_Decode` 是**自研 AES-256-CBC**：解密一块后与本块**前一块的密文（IV 链）**异或得到明文，再把"本块原始密文"存回 IV 供下一块用（标准 CBC 解密流程）。每块 16 字节、14 轮。第 0 块解密出的前 16 字节里 `[12..15]` 存放 **App 长度**，供 Bootloader 知道要写多少内部 Flash。
**追问**：CBC 和 ECB 区别？（ECB 相同明文→相同密文、可被判模式；CBC 链式、更安全。）**致命问题**：你们 Key/IV 是硬编码 `0x31 0x32...`（ASCII "1212..."），且只有加密**没有签名验签**——生产必须改：密钥安全存储（OTP/加密区）、增加 **固件签名（RSA/ECDSA）+ Hash(SHA256)** 防篡改与伪造升级。

### Q23. 只加密不签名能防什么、不能防什么？一个安全的 OTA 还应加什么？
**答**：加密防"被看懂/抄走算法"，**不防"被替换/篡改"**。安全 OTA 应：① 固件 **签名验签**（Bootloader 用预埋公钥验签名，失败绝不跳转）；② **哈希校验**（SHA256 比对）；③ **版本/防回滚**（EEPROM 记版本号，拒绝降级）；④ **A/B 双区 + 成功标记**（新固件跑稳后再提交，否则回滚）；⑤ 密钥不硬编码。

## 七、低功耗 / 稳定性 / 调试

### Q24. STM32F411 有哪几种低功耗模式？你们项目为什么没用？手表该怎么加？
**答**：Sleep（内核停）、Stop（时钟停、RAM 保持、唤醒快）、Standby（几乎全断、RAM 丢、靠备份域/RTC 唤醒）。本项目是常亮 OTA/调试形态，没进低功耗。**手表**应：按键/RTC/串口唤醒进 Stop，关闭无关外设时钟，`led_blink_task` 用 RTC 闹钟替代 `vTaskDelay` 轮询，必要时 Standby + 极低漏电。唤醒后注意重新初始化被关闭的时钟/外设。
**追问**：Stop 模式 SysTick 还跑吗？（不跑，需外部中断/RTC 唤醒；唤醒要重配时钟树。）

### Q25. 看门狗你们怎么用的？独立看门狗 IWDG 和窗口看门狗 WWDG 区别？
**答**：本项目用"Bootloader 看门狗"在 App 写回 `0x00` 后强制复位。`IWDG` 独立 LSI 时钟、溢出即复位、喂狗时间自由（防死机）；`WWDG` 挂 APB1、必须在**窗口内**喂（防程序跑飞后刚好在错误时刻喂狗）。量产建议：关键任务定期喂 IWDG，且把"喂狗"放在最不容易假活的路径上。
**追问**：RTOS 里看门狗该由谁喂？（单独一个高优先级看门狗任务，或空闲任务钩子；不能只由某个业务任务喂，否则它卡了没人复位。）

### Q26. 你们怎么调试？`printf` 重定向、RTT、栈溢出分别怎么处理？
**答**：`__io_putchar`→`USART1_SendByte`（printf 重定向到串口）；也接了 **SEGGER RTT**（不占串口、近乎零开销，但需 J-Link/RTT Viewer）。日志走 **EasyLogger**（异步缓冲、分级）。调试 HardFault：看 `fault` 寄存器（CFSR/HFSR/MMFAR/BFAR）定位 PC；栈问题开 `configCHECK_FOR_STACK_OVERFLOW=2`。
**追问**：printf 在 ISR 里会有什么问题？（阻塞、可能重入、占 ISR 时间；本项目 USART1 IRQ 里有回显 printf，高波特率下会拖慢中断，应去掉或只留 RTT。）

### Q27. 你们工程里有一大堆"写了但没调用"的代码（LED 框架、KEY 中断、ADC/DMA、USART 解析），你怎么看这种现象？
**答**：这是典型的"边探索边留模板"——快速验证 SPI/KEY/DMA 时写的框架没清理，最后 OTA 主路径只用了其中一小部分。维护风险：① 增加编译体积与认知负担；② 死代码里藏着真 bug（如 `EXTI0_IRQHandler` 里用 `xTaskGetTickCount()` 而非 FromISR 版、`key_task` 把同一静态结构指针反复入队）；③ 新人易被误导。建议：把可复用部分抽成独立库（BSP 组件），死代码删除或加单测。
**追问**：你会怎么说服团队做这轮清理？（用 map 文件证明体积、列具体 bug、先补测试再删。）

## 八、C 语言 / 嵌入式基础（3 年必会）

### Q28. `volatile` 在你项目里哪些地方必须用？
**答**：① `main.c` 的 `static __IO uint32_t uwTimingDelay`（被中断递减）；② 内存映射寄存器（`GPIOx->ODR` 等，编译器不能假设不变）；③ 多任务共享且被优化掉的变量；④ ISR 与任务共享的标志。**追问**：`volatile` 能保证原子性吗？（不能，只防优化；多任务/中断共享仍需临界区或原子操作。）

### Q29. 结构体/联合体在协议解析里怎么用？对齐（alignment）踩过坑吗？
**答**：Ymodem 包是字节流，解析时用偏移宏（`PACKET_HEADER/PACKET_SEQNO_INDEX`）而非直接强转结构体，避免**对齐**与**大小端**问题。Cortex-M4 支持非对齐访问但有性能/正确性隐患，跨总线（如 DMA 描述符）必须 `__packed` 或手动拼字节（本项目 `pdata[i]` 用 `memcpy`/移位拼 32 位，规避对齐 UB）。
**追问**：`*(uint32_t*)pTemp` 把 `uint8_t*` 强转成 `uint32_t*` 读有什么风险？（未对齐/别名违规 UB；本项目 `flash_write` 用 4 字节地址是按 Flash 编程要求，且地址 4 对齐，安全；但通用场景要用 `memcpy`。）

### Q30. 临界区（critical section）在 FreeRTOS 怎么进？和关中断的区别？
**答**：任务里用 `taskENTER_CRITICAL()/taskEXIT_CRITICAL()`（屏蔽≤`MAX_SYSCALL` 优先级的中断、可嵌套）；ISR 里用 `taskENTER_CRITICAL_FROM_ISR()/taskEXIT_CRITICAL_FROM_ISR()` 并返回之前的 BASEPRI。区别：临界区**不关所有中断**（只关到阈值），且能在临界区里调 FreeRTOS API；而 `__disable_irq()` 关一切、临界区里不能调内核 API。
**追问**：临界区里能 `vTaskDelay` 吗？（不能，会死锁。）

### Q31. 大端/小端在 OTA 里哪里会遇到？
**答**：App 长度在密文头里是 4 字节，本工程用 `AppSize=(pTemp[15]<<24)|...|pTemp[12]` **手动大端拼**，说明固件头的多字节字段是大端；Ymodem CRC、包号也都是按字节流处理。跨平台传输必须**显式规定字节序**并手动拼/拆，不能依赖本机大小端。

## 九、系统设计 / 项目经验（行为面）

### Q32. 如果让你重做这套 OTA，你会怎么改得更稳？
**答**（结合本项目坑）：① **统一 Bootloader/App 地址表**到一份头文件，杜绝 0x08008000 vs 0x08010000 错位；② 加 **签名+哈希** 校验，密钥安全存储；③ 改 `flash_erase` 越界、开栈溢出检测、加 `vApplicationStackOverflowHook`；④ 把 Ymodem 下载与 Flash 写入**解耦成消费者任务**，OTA 命令响应不被下载阻塞；⑤ A/B 双区 + 成功提交位，支持回滚；⑥ 死代码清理成独立 BSP 库；⑦ 低功耗：未升级时进 Stop，按键/RTC 唤醒。

### Q33. 你在这个项目里"最能讲清楚的一个难点"是什么？
**答（示例）**：串口在两种模式间切换——命令阶段用"DMA+IDLE 一次性收定长帧"，下载阶段切"轮询 DR 跑 Ymodem"。难点在于两套机制会抢同一个 USART DR 且 IDLE 会污染命令队列，必须严格按顺序 `EnterRxMode`（关 DMA/IDLE/清残留）→ 下载 → `RestoreDmaMode`（重开）。这本质上是"**同一外设在不同业务阶段用不同驱动策略**"的资源互斥问题，用状态机 + 显式开关解决了。

### Q34. 你怎么验证一次 OTA 升级真的成功、且掉电能恢复？
**答**：① 单元测试：AES 加解密往返、W25Q64 读写比对、CRC 一致性；② 集成测试：模拟断电（下到一半拔电）→ 重启 → 确认状态字停在 `0x11/0x22` → App 自检触发复位 → Bootloader 重下或回滚；③ 边界：固件长度边界、CRC 错误包、签名失败；④ 现场：`vTaskGetStackHighWaterMark` 验证栈、`configASSERT`/看门狗兜底。

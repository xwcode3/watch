# 软件 IIC（GPIO 模拟）通信时序规范

> **一句话结论**：软件 IIC 所有时序歧义的根因只有一条——**I2C 规定 SDA 只能在 SCL 低电平时变化，唯一例外是 START（SCL 高时 SDA 下降沿）和 STOP（SCL 高时 SDA 上升沿）**。因此，消除歧义的核心手段是给每个时序原语（起始/停止/发字节/收字节/等 ACK/发 ACK）定一个**统一的收尾契约：退出时 SCL=0、SDA=释放(高)**，让任意两个原语拼接都不会继承上一个原语遗留的中间电平。

本文档总结软件 IIC 的规范做法，并对照本工程 `Core/Src/iic.c` 的实际实现标注隐患点（**只标注、不改代码**）。

---

## 一、结论先行（TL;DR）

软件 IIC 要"时序不歧义"，牢牢守住三条规则即可：

| # | 规则 | 说明 |
|---|------|------|
| 1 | **SDA 只在 SCL 低电平时变化** | 唯一例外是 START / STOP 两个边沿，它们必须在 SCL 高电平时发生 |
| 2 | **收尾契约：每个原语退出时 SCL=0、SDA=释放(高)** | 下一个原语从头开始，不继承上一个的中间电平 |
| 3 | **SDA 输入/输出方向切换只能在 SCL 低电平时进行，且切换后立即置为明确的释放态** | 切换方向是软件 IIC 最容易踩坑的点 |

所谓"时序歧义"，本质是：**上一个阶段结束时 SDA/SCL 遗留的电平，被下一个阶段误读成 START、STOP、某个数据位或某个 ACK**。只要每个阶段"干净收尾"，歧义就无从产生。

---

## 二、根因：为什么软件 IIC 会"时序歧义"

### 2.1 硬件 I2C 控制器 vs 软件模拟

- **硬件 I2C**：外设控制器内部有状态机，自动保证 SCL/SDA 的时序约束（数据建立时间、保持时间、START/STOP 条件等），你只管往数据寄存器里塞字节。
- **软件模拟**：这些约束**全都要靠你自己用 GPIO 拉高拉低去保证**。任何一处"忘记拉低 SCL""忘记释放 SDA"都会破坏时序。

### 2.2 总线状态模型

I2C 总线只有两种状态：

- **空闲态**：SCL = 高、SDA = 高（靠上拉电阻维持，主机和从机都释放总线）。
- **忙态**：发生 START 之后、STOP 之前。

数据线 SDA 的电平**只在 SCL 低电平时才允许被改变**；SCL 高电平时，SDA 必须稳定，此时从机会对 SDA 采样（数据位）或识别边沿（START/STOP）。

### 2.3 "歧义"的定义与后果

| 遗留电平组合 | 被误读成 | 后果 |
|---|---|---|
| SCL 高 + SDA 从高变低 | START | 从机误以为开始一帧新传输，之前的字节作废 |
| SCL 高 + SDA 从低变高 | STOP | 从机提前结束当前传输 |
| 发完字节后 SDA 残留低电平 | 数据位 0 / 假 ACK | 下一位数据被污染，或 ACK 判断错误 |
| ACK/NACK 后 SDA 残留低 | 下字节第一位被拉低 | 收到的第一个 bit 恒为 0 |

## 三、三条根本规则（详细）

### 规则 1：SDA 只在 SCL 低电平时变化

- 发送数据位：先 SCL=0 → 设 SDA → 再 SCL=1（锁存）→ 再 SCL=0。
- 读取数据位：先 SCL=0 → SCL=1 → 在 SCL 高电平期间采样 SDA → 再 SCL=0。
- **START/STOP 是唯一例外**：它们刻意在 SCL 高电平时制造 SDA 的边沿，这是 I2C 协议定义的控制信号。

### 规则 2：收尾契约（本文档的核心）

**每个原语退出时，总线必须回到一个"安全默认态"：SCL = 0，SDA = 释放（高电平）。**

为什么 SCL 一定要是 0？
- SCL=0 时，SDA 随便怎么变都不会产生 START/STOP，是"安全区"。

为什么 SDA 一定要释放（高）？
- 释放 = 主机不驱动 SDA（切输入，或开漏输出高），把总线交还给"空闲/从机驱动"的状态。这样下一个原语的第一个动作可以无歧义地接管 SDA。

### 规则 3：方向切换只在 SCL 低电平时做，且切换后立即置释放态

软件 IIC 有两种 SDA 处理方式，各有各的坑：

- **方式 A：全程开漏输出 + 读 IDR**
  SDA 始终配成"开漏输出"。输出高 = 释放总线（靠外部上拉维持高），输出低 = 驱动低。读数据时用 `GPIO_ReadInputDataBit` 读输入数据寄存器（IDR），而不是读输出寄存器。
  **坑**：读数据前，ODR 必须是 1（释放），否则主机自己把 SDA 拉低，从机永远无法把数据拉高，读出来全是 0。

- **方式 B：读写方向动态切换**
  写时 SDA 配输出，读时 SDA 配输入（释放）。用 `GPIO_Init` 或 MODER 寄存器切换。
  **坑**：`GPIO_Init` 重新配置方向时**不保证清掉 ODR**。切换回输出后，SDA 电平可能残留上一次输出的值，必须紧接着显式 `SetBits` 置高释放。

> 本工程 `iic.c` 恰好两种方式各有一套：小写 `i2c_*` 用**方式 A**，大写 `IIC*` 用**方式 B**（见第六节）。

## 四、各阶段标准时序（逐阶段精讲）

下文中：
- `SDA=0/1` 表示主机把 SDA 驱动为低/高；
- `SDA=Z` 表示主机释放 SDA（切输入或开漏输出高），总线电平由从机或上拉电阻决定；
- 每个阶段末尾都标注【收尾】状态，这是消除歧义的关键。

### 4.1 起始条件 START

```
SCL:   1 ──────────┐______
SDA:   1 ────┐      │
             └──────┘
         (SCL 高时 SDA 高→低 = START)
```

| 步骤 | 操作 |
|---|---|
| 1 | 确保空闲态：SCL=1、SDA=1 |
| 2 | SDA=0（此时 SCL 仍为高 → 产生下降沿 = START） |
| 3 | SCL=0（进入忙态，准备传数据） |

【收尾】`SCL=0，SDA=0`（这是唯一 SDA 收尾为 0 的合法原语，因为 START 后紧接着就要发数据位，SCL 已是低电平，安全）。

**易错点**：忘记先置空闲态就拉 SDA，导致边沿不成立；或 START 后没把 SCL 拉低就直接发数据。

### 4.2 发送一个字节（8 bit，MSB first）

```
        bit7  bit6  ...   bit0   释放SDA等ACK
SCL:   __▔▔▔__▔▔▔__ ... __▔▔▔__▔▔▔____
SDA:    X    X     ...   X      Z(高)
         ↑SCL高时SDA必须稳定，从机采样
```

| 步骤 | 操作 |
|---|---|
| 循环 8 次 | ① SCL=0 → ② SDA=当前 bit（0 或 1）→ ③ SCL=1（锁存）→ ④ SCL=0 → ⑤ 移位取下一 bit |
| 循环后 | **释放 SDA（SDA=Z/高）**，把总线让给从机，准备第 9 个时钟读 ACK |

【收尾】`SCL=0，SDA=释放(高)`。

**易错点**：
1. **发完第 8 位没释放 SDA**——这是最常见、后果最隐蔽的坑。若不释放，主机仍驱动 SDA，从机无法拉低 ACK，且下一字节第一位被污染。
2. 数据位顺序搞反（先发 bit0 而不是 bit7）。
3. SDA 在 SCL 高电平时才改变（应在 SCL 低时改变）。

### 4.3 等待 ACK（主机收从机应答，第 9 个时钟）

| 步骤 | 操作 |
|---|---|
| 1 | 释放 SDA（SDA=Z），从机将驱动 ACK 电平 |
| 2 | SCL=1（第 9 个时钟），从机此时把 SDA 拉低=ACK、保持高=NACK |
| 3 | 采样 SDA |
| 4 | SCL=0 |
| 5 | **SDA 恢复主机控制，并置为释放(高)** |

【收尾】`SCL=0，SDA=释放(高)`。

**易错点**：
1. 等待 ACK 前没有释放 SDA（继承了发字节残留的低电平）→ 永远读到"假 ACK"（低）。
2. **ACK 阶段结束后切回输出模式时，没显式置高 SDA**，ODR 残留导致下一阶段电平不确定。
3. 返回值的语义混乱（0=ACK 还是 1=ACK），导致上层判断写反。本工程两套函数恰好相反（见 6.2）。

### 4.4 接收一个字节（8 bit，MSB first）

| 步骤 | 操作 |
|---|---|
| 循环 8 次 | ① SCL=0 → ② 释放 SDA（SDA=Z，从机放数据）→ ③ SCL=1 → ④ 在 SCL 高电平期间采样 SDA 读入 1 bit → ⑤ SCL=0 → ⑥ 移位 |
| 循环后 | SDA 切回输出并释放（SDA=高） |

【收尾】`SCL=0，SDA=释放(高)`。

**易错点**：
1. 读数据时 SDA 没有真正释放（开漏 ODR 没置 1，或没切输入）→ 读到全 0。
2. 在 SCL 低电平或 SCL 刚拉高的瞬间采样，数据还没稳定。
3. 读完没把 SDA 切回输出/释放，影响后续 ACK 阶段。

### 4.5 发送 ACK / NACK（主机回从机，第 9 个时钟）

| 步骤 | 操作 |
|---|---|
| 1 | SCL=0 |
| 2 | SDA=0（ACK，告诉从机继续发）/ SDA=1（NACK，告诉从机停止） |
| 3 | SCL=1（第 9 个时钟） |
| 4 | SCL=0 |
| 5 | **释放 SDA（SDA=高）** |

【收尾】`SCL=0，SDA=释放(高)`。

**易错点**：ACK/NACK 之后**不释放 SDA**。若刚发了 ACK（SDA=0）就直接进 STOP 或下一字节，SDA 的低电平残留会破坏后续时序。

### 4.6 停止条件 STOP

```
SCL:   ____▔▔▔▔▔▔▔▔▔▔▔
SDA:   ____┐          ▔▔▔▔▔
           └────────┘
              (SCL 高时 SDA 低→高 = STOP)
```

| 步骤 | 操作 |
|---|---|
| 1 | SCL=0 |
| 2 | SDA=0 |
| 3 | SCL=1 |
| 4 | SDA=1（SCL 高时 SDA 低→高 = STOP 上升沿） |

【收尾】`SCL=1，SDA=1`（回到空闲态，这是唯一 SCL 收尾为 1 的合法原语）。

**易错点**：STOP 前忘记先 SCL=0、SDA=0，直接从高电平 SCL 上抬 SDA，边沿不成立；或 STOP 后总线没回到空闲态。

## 五、收尾契约总表

这张表是本文档的灵魂，也是排查"时序歧义"的速查表。**任何软件 IIC 原语退出时都必须符合下表，否则就是隐患**：

| 原语 | 退出时 SCL | 退出时 SDA | 备注 |
|---|---|---|---|
| START | 0 | 0 | 唯一 SDA=0 的合法收尾（紧接着发数据） |
| STOP | 1 | 1 | 唯一 SCL=1 的合法收尾（回到空闲态） |
| 发送字节 | 0 | 释放(高) | 必须释放，等 ACK |
| 等待 ACK | 0 | 释放(高) | 切回输出后必须显式置高 |
| 接收字节 | 0 | 释放(高) | 切回输出后必须显式置高 |
| 发送 ACK | 0 | 释放(高) | ACK 之后必须释放 |
| 发送 NACK | 0 | 释放(高) | NACK 之后必须释放 |

> 记忆口诀：**"进出都在低电平时动手，中间只有 START/STOP 敢在高电平时翻脸；每次收尾 SCL 归零、SDA 松手。"**

## 六、对照本工程 `Core/Src/iic.c` 的分析

`iic.c` 里并排两套软件 IIC 实现，这是理解本项目时必须先分清的前提：

| 套件 | 命名 | 引脚来源 | SDA 处理方式 | 服务对象 |
|---|---|---|---|---|
| 小写套件 | `i2c_Start/Stop/SendByte/ReadByte/WaitAck/Ack/NAck` | 宏 `EEPROM_I2C_*`（PB8/PB9） | 方式 A：全程开漏输出 + 读 IDR | AT24CXX（EEPROM） |
| 大写套件 | `IICStart/Stop/SendByte/ReceiveByte/WaitAck/SendAck/SendNotAck` | `iic_bus_t` 结构体 | 方式 B：SDA 输入/输出动态切换 | AHT21（`bsp_aht21_driver.c` 挂载） |

AHT21 驱动 `bsp_aht21_driver.c` 里挂载的是**大写套件**（`pf_iic_start → IICStart` 等）。

### 6.1 大写 `IIC*` 套件逐函数收尾分析（AHT21 实际使用）

| 原语 | 退出时 SCL | 退出时 SDA | 是否规范 | 隐患 |
|---|---|---|---|---|
| `IICStart` | 0 | 0（输出） | ✅ | 无 |
| `IICStop` | 1 | 1（输出） | ✅ | 无 |
| `IICSendByte` | 0 | **残留最后 bit0 的 ODR** | ❌ | 发完字节未释放 SDA，SDA 停在最后一个数据位 |
| `IICWaitAck` | 0 | **输出模式但 ODR 残留** | ❌ | 结尾 `SDA_Output_Mode` 只改方向未置高，SDA 电平不确定 |
| `IICReceiveByte` | 0 | **输出模式但 ODR 残留** | ❌ | 结尾 `SDA_Output_Mode` 只改方向未置高 |
| `IICSendAck` | 0 | 0（输出） | ❌ | ACK 后未释放 SDA |
| `IICSendNotAck` | 0 | 1（输出） | ⚠️ | SDA=1 算释放，但依赖外部上拉电阻 |

**核心结论**：大写套件的 START/STOP 收尾正确，但**发送字节、等待 ACK、接收字节、发送 ACK 四个原语都违反了"收尾契约"**——它们退出时 SDA 没有回到"释放(高)"。

**为什么 AHT21 现在还能跑通？** 因为当前 AHT21 的调用序列里，每个原语**开头**恰好都重新显式设置了 SDA（`IICSendByte` 开头先 `SCL=0` 再 `SDA_Output`、`IICReceiveByte` 开头 `SDA_Input_Mode`、`IICStop` 开头 `SDA_Output(0)`），把上一个原语遗留的电平"覆盖"掉了。**这是靠调用顺序碰巧自洽，不是靠原语契约保证**——一旦更换调用顺序、或将来复用这些原语写其他设备，歧义就会爆发。这正是你说的"不同通信阶段相互影响"的本质。

### 6.2 小写 `i2c_*` 套件逐函数收尾分析（EEPROM 使用）

| 原语 | 退出时 SCL | 退出时 SDA | 是否规范 |
|---|---|---|---|
| `i2c_Start` | 0 | 0 | ✅ |
| `i2c_Stop` | 1 | 1 | ✅ |
| `i2c_SendByte` | 0 | 1（`i==7` 时显式释放） | ✅ |
| `i2c_WaitAck` | 0 | 1 | ✅ |
| `i2c_Ack` | 0 | 1（显式释放） | ✅ |
| `i2c_NAck` | 0 | 1 | ✅ |
| `i2c_ReadByte` | 0 | 1（继承之前释放态） | ✅ |

小写套件整体收尾是**规范**的——每个原语退出时 SCL=0、SDA=1，符合收尾契约。但它仍有一个隐患：读数据用 `GPIO_ReadInputDataBit` 读 IDR，**依赖 ODR 恒为 1（释放）**；一旦某处意外把 ODR 写成 0，读数据会全 0。方式 A 的固有风险。

### 6.3 语义歧义：两套函数 ACK 返回值相反

这是比电平歧义更隐蔽的"语义歧义"：

| 函数 | 返回 0 | 返回 1 |
|---|---|---|
| 小写 `i2c_WaitAck` | **收到 ACK** | **NACK/超时** |
| 大写 `IICWaitAck` | **NACK/超时（失败）** | **收到 ACK（成功）** |

`bsp_aht21_driver.c` 里为此专门留了注释纠正：

```c
// NOTE: IICWaitAck returns 1 = ACK received, 0 = NACK/timeout.
//       (Do NOT compare against AHT21_OK(0) — that was inverted!)
```

两套同名（大小写）函数、相反的返回值语义，是维护上的定时炸弹。规范做法是**统一一套返回值约定**（如 `0=成功/ACK`），不要出现两套相反约定。

### 6.4 其他可标注的写法问题（不修改，仅记录）

1. `IICSendByte` / `IICReceiveByte` 用 `cSendByte += cSendByte` 代替 `<<= 1`、`cR_Byte += cR_Byte` 代替 `<<= 1`（注释里也写了"修正：左移一位"但被改回 `+=`）。对 `uint8_t` 二者结果等价，但语义不清晰，易误导维护者。
2. `SDA_Output_Mode` / `IICInit` 里 `GPIO_OType = GPIO_OType_OD`（开漏）但 `GPIO_PuPd = GPIO_PuPd_NOPULL`（无内部上拉），**依赖外部上拉电阻**。若硬件没有外部上拉，SDA 释放时电平浮空，读数据不可靠。这也是软件 IIC 要留意的一点（见 7.2）。
3. 大写套件用 `GPIO_Init` 做 SDA 方向切换，开销大、且不保证 ODR 清零，是残留电平问题的直接来源。更稳的做法是用寄存器（`MODER`）或 `GPIO_SetBits` 在切回输出后立即置高。

## 七、常见时序歧义场景 Checklist

排查软件 IIC 问题时，按此清单逐项核对：

- [ ] **发送字节后是否释放 SDA？**（否则读 ACK 必失败/假 ACK）
- [ ] **等待 ACK 前是否释放 SDA？**
- [ ] **ACK/NACK 之后是否释放 SDA？**
- [ ] **读字节时 SDA 是否真正处于释放态**（开漏 ODR=1 或切输入）？
- [ ] **SDA 方向切换是否发生在 SCL 低电平期间？切换后是否显式置高？**
- [ ] **每个原语退出时 SCL 是否为 0（除 STOP）？**
- [ ] **START/STOP 的边沿是否在 SCL 高电平时产生？**
- [ ] **数据位是否在 SCL 高电平时保持稳定（建立/保持时间足够）？**
- [ ] **SDA 高电平是否有外部上拉电阻兜底（开漏 + 无内部上拉时）？**
- [ ] **ACK 返回值语义是否统一、是否与上层判断一致？**
- [ ] **延时是否足够**（400kHz 下位周期约 2.5µs，软件延时需按主频校准）？

### 7.1 上拉电阻（硬件前提）

软件 IIC 用开漏输出模拟时，**高电平完全依赖外部上拉电阻**。没有上拉 → SDA/SCL 高电平浮空 → 时序全乱。这是"软件时序写得对但就是读不到数据"最常见的硬件根因。AHT21 模块板通常自带 4.7k/10k 上拉。

### 7.2 时钟速率与延时

标准模式 100kHz、快速模式 400kHz、快速+ 1MHz。软件模拟用 `delay_us`/空循环实现，需按实际主频校准（本工程 `i2c_Delay()` 空循环 40 次适配 168MHz 下约 400kHz）。延时过短会违反建立/保持时间，过长则速率下降。

## 八、推荐标准实现模板（参考，不修改现有代码）

下面给出一套**收尾契约严格合规**的软件 IIC 参考模板（伪代码，供将来重构或新驱动参考）。关键点都在注释里标出：

```c
/* ---- 方向切换：只改方向，改完立刻置释放态 ---- */
static void sda_out(void) { /* SDA 配开漏输出 */ GPIO_SetBits(SDA); }
static void sda_in(void)  { /* SDA 配输入(释放) */ }

/* ---- 起始：SCL 高时 SDA 高→低 ---- */
void iic_start(void) {
    sda_out(); SDA=1; SCL=1; delay;
    SDA=0;      delay;          /* START 边沿 */
    SCL=0;      delay;          /* 收尾：SCL=0 */
}

/* ---- 停止：SCL 高时 SDA 低→高 ---- */
void iic_stop(void) {
    SCL=0; SDA=0; delay;        /* 先进入安全态 */
    SCL=1;      delay;
    SDA=1;      delay;          /* STOP 边沿 */
    /* 收尾：总线空闲 SCL=1 SDA=1 */
}

/* ---- 发字节：发完释放 SDA ---- */
void iic_send_byte(uint8_t b) {
    for (int i = 0; i < 8; i++) {
        SCL=0; delay;
        SDA = (b & 0x80) ? 1 : 0; delay;
        SCL=1; delay;           /* 锁存 */
        SCL=0; delay;
        b <<= 1;
    }
    SDA=1; delay;               /* ★释放 SDA，等 ACK */
    /* 收尾：SCL=0 SDA=释放 */
}

/* ---- 等 ACK：释放 SDA → 拉高 SCL 采样 → 恢复并释放 ---- */
uint8_t iic_wait_ack(void) {
    sda_in();                   /* 释放 SDA */
    SCL=1; delay;
    uint8_t ack = (SDA == 0);   /* 0=ACK */
    SCL=0; delay;
    sda_out(); SDA=1;           /* ★切回输出并立即置高 */
    return ack;                 /* 统一约定：1=ACK */
}

/* ---- 收字节：先释放 SDA，SCL 高时采样 ---- */
uint8_t iic_read_byte(void) {
    uint8_t v = 0;
    sda_in();                   /* 释放 SDA，从机驱动数据 */
    for (int i = 0; i < 8; i++) {
        SCL=0; delay;
        SCL=1; delay;           /* 从机放数据 */
        v = (v << 1) | (SDA ? 1 : 0);
        SCL=0; delay;
    }
    sda_out(); SDA=1;           /* ★切回输出并立即置高 */
    return v;
}

/* ---- 发 ACK / NACK：发完释放 SDA ---- */
void iic_send_ack(uint8_t ack) {   /* ack=0 表示 ACK */
    SCL=0; SDA = ack ? 1 : 0; delay;
    SCL=1; delay;
    SCL=0; delay;
    SDA=1; delay;               /* ★释放 SDA */
}
```

> 模板中所有带 ★ 的行，就是本工程大写 `IIC*` 套件**缺失**的"释放 SDA / 置高收尾"动作，也是消除时序歧义的关键。

## 九、AHT21 专属时序注意点

在通用软件 IIC 规范之外，AHT21 还有几处容易踩坑的协议细节：

1. **触发测量命令后必须等待测量完成**：发送 `0xAC 0x33 0x00` 触发测量后，芯片需要约 75~80ms 才能完成转换。期间读状态字的 bit7（忙标志）为 1，需轮询等待变为 0 再读数据。本工程 `AHT21_MEASURE_WAITING_TIME=80ms`。
2. **软复位命令**：`0xBE` 后需延时 10ms 再操作。
3. **读数据用读地址 0x71，写命令用写地址 0x70**（7bit 地址 0x38 左移 + R/W 位）。
4. **读完最后一个字节回 NACK**（不是 ACK），告诉从机主机读完了，然后 STOP。本工程 `aht21_read_data` 里 6 字节读完后 `pf_iic_send_no_ack` 正确。
5. **状态轮询读取**是"起始 + 读地址 + 收 1 字节 + NACK + 停止"的独立事务，注意它和主读取事务之间要各自完整 START/STOP，不要用重复 START 串扰。

## 十、大厂正规做法参照（ST / NXP / ESP-IDF / WCH / Linux 内核）

> 说明：I2C 与 IIC 是同一协议（Inter-Integrated Circuit）的两种写法，本节引述大厂原始资料时沿用其习惯写法 I2C，与正文 IIC 同义。

软件 IIC 没有"官方唯一标准"，但各大厂与 Linux 内核积累了一套高度一致的工程规范。其中最权威的参考实现是 Linux 内核的 `drivers/i2c/algos/i2c-algo-bit.c`（Simon Vogl 1995 年实现，至今被几乎所有的软件 I2C 驱动沿用其算法）。下面把大厂做法提炼成可直接对照的要点。

### 10.1 祖师爷：Linux 内核 i2c-algo-bit 的四个设计要点

**① 4 回调抽象，硬件解耦**

内核不直接操作 GPIO，而是抽象出四个回调，硬件差异由调用方注入：

```c
struct i2c_algo_bit_data {
    void  *data;
    void (*setsda)(void *data, int state);   /* 驱动 SDA */
    void (*setscl)(void *data, int state);   /* 驱动 SCL */
    int  (*getsda)(void *data);              /* 读 SDA */
    int  (*getscl)(void *data);              /* 读 SCL（可选，用于时钟拉伸） */
    int   udelay;      /* 半时钟周期 µs：快速模式≥2、标准模式≥5 */
    int   timeout;     /* 超时，单位 jiffies */
};
```

对照本工程：大写 `IIC*` 套件的 `iic_bus_t` + 函数指针正是这个思路；小写 `i2c_*` 套件硬编码 `EEPROM_I2C_*` 宏则不是。

**② 拉高 SCL 后"读回确认"——时钟拉伸检测 + 超时**

这是内核实现里最关键、最容易被初学者漏掉的一段：

```c
static int sclhi(adap) {
    setscl(adap, 1);
    start = jiffies;
    while (!getscl(adap)) {             /* 从机可能把 SCL 拉低（时钟拉伸） */
        if (time_after(jiffies, start + adap->timeout))
            return -ETIMEDOUT;          /* 超时退出，绝不无限等待 */
    }
    udelay(adap->udelay);
}
```

核心思想：**SCL 拉高后不是"我以为高了就高了"，而是读回 `getscl` 确认它真的高了**。这一步同时解决两个问题——时钟拉伸（从机没准备好时拉低 SCL，主机必须等）和总线卡死（超时兜底，不挂死系统）。

**③ 每个原语开头显式 assert 前置状态（"收尾契约"的代码化）**

```c
static void i2c_start(adap)    { /* assert: scl, sda are high */ ... }
static void i2c_repstart(adap) { /* assert: scl is low */        ... }
static void i2c_stop(adap)     { /* assert: scl is low */        ... }
```

大厂不靠"调用顺序碰巧对"，而是**显式声明每个原语依赖的前置状态**。这正好是本文档"收尾契约"的一体两面：上一个原语收尾 = 下一个原语的前置条件。

**④ 可配置半周期延时**

`adap->udelay` 由外部注入（快速模式≥2µs、标准模式≥5µs），而非写死空循环——便于同一套算法适配不同主频。

### 10.2 大厂五大共识规范（对照本工程）

| # | 规范 | 大厂依据 | 本工程现状 |
|---|---|---|---|
| 1 | 开漏输出 + 外部上拉 | ST 官方：内部上拉约 40kΩ 太弱，外部 2.2k~10k | 开漏 + NOPULL，依赖模块板外部上拉 ⚠️ 需确认 |
| 2 | SDA 方向动态切换，切在 SCL 低时 | WCH 软 I2C：发=输出、收=输入上拉 | 大写套件有，但切换后未置释放态 ❌ |
| 3 | 时钟拉伸检测 + 超时 | Linux `sclhi`、ESP-IDF 默认 10ms 超时 | 无 SCL 读回，超时仅 5µs ❌ |
| 4 | 总线恢复（9 时钟脉冲 + STOP） | NXP 规范、ESP-IDF `recover_i2c_bus` | 无 ❌ |
| 5 | 重复起始 Sr（读寄存器必须） | NXP：发 STOP 会重置从机寄存器指针 | 无 `repstart`，用 STOP+START 代替 ⚠️ |

### 10.3 上拉电阻选型（ST 官方数据，可直接抄）

开漏输出下，高电平完全靠上拉电阻，阻值决定了上升时间与速率上限。

| 模式 | 速率 | 推荐起始值 | 备注 |
|---|---|---|---|
| 标准模式 | 100 kHz | 4.7 kΩ | 上升时间 tr ≤ 1000 ns |
| 快速模式 | 400 kHz | 2.2 kΩ | tr ≤ 300 ns，短总线可降至 1.2~1.5 kΩ |
| 内部上拉 | — | 约 40 kΩ | 只够低速短距离凑合，正式设计必须外部上拉 |

阻值上下限由两个约束决定：

- **下限 Rmin**（灌电流约束）：`Rmin = (Vdd - Vol) / Iol`。Vol ≤ 0.4V，Iol 取 3mA（I2C 规范）→ 3.3V 下约 967Ω。
- **上限 Rmax**（上升时间约束）：`Rmax = tr / (0.8473 × Cbus)`。Cbus 典型 100~200pF（每器件 10~40pF，规范上限 400pF）。400kHz 下 Cbus=100pF 时 Rmax ≈ 3.5kΩ。

> 排查经验（ST 官方 FAQ）：上拉到 100kΩ 会看到明显错误的时序；上升沿 >500ns 就该减小阻值；设计时应实测上升/下降时间反推。

### 10.4 最值得补进本工程的四个"大厂动作"（按投入产出比排序）

1. **时钟拉伸检测**（`sclhi` 读回 SCL）——解决"时序歧义"之外的第二个大坑，尤其接慢速从机时。
2. **总线恢复函数**——SDA 被从机拉死时，发 9 个 SCL 脉冲把从机踢回空闲 + STOP，一键救回挂死的总线。
3. **原语 assert 前置状态**——把本文档的"收尾契约"从文字落到代码注释/断言，杜绝"碰巧自洽"。
4. **重复起始 Sr**——规范读寄存器流程（AHT21 当前 STOP+START 可用，但 Sr 才是标准做法）。

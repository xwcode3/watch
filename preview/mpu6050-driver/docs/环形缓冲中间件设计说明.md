# 环形缓冲中间件（mid_ringbuf）设计说明

> 适用范围：将 `app/BSP/USART/mid_circular_buffer.c` 的环形数组思路，升级为一份**可独立编译、零堆依赖、面向 MPU6050 数据接收**的通用 FIFO 中间件。
> 位置：`preview/mpu6050-driver/middleware/ringbuf/mid_ringbuf.{h,c}`
> 状态：`gcc -Wall -Wextra` 0 warning；本地逻辑自测 60+ 项断言全部通过。

---

## 1. 为什么要重写，而不是直接用原来的

原 `mid_circular_buffer` 思路是对的，只是有几个点不适合直接搬到 MPU6050 接收链路：

| 维度 | 原 mid_circular_buffer | 新版 mid_ringbuf |
|---|---|---|
| 存储分配 | `malloc` 动态分配 | **外部传入存储**，零堆依赖（嵌入式常关堆/静态段） |
| 日志依赖 | 强依赖 `elog.h` 的 `log_e` | 日志宏 `RINGBUF_LOG_E` 默认空，可重定向 |
| 索引回绕 | `(head+1) % SIZE` 取模 | 容量取 2 的幂，`(head+1) & mask` 代替取模（更快） |
| 判满 | 牺牲一槽，`(head+1)%N == tail` | **同思路**：`(head+1)&mask == tail`，保留牺牲一槽 |
| 长度推导 | 无 `count`，由 head/tail 推导 | **同思路**：`used = (head - tail) & mask`，无 `count` 字段 |
| 整帧写入 | 只有单字节 `ring_push_head` | **新增 `ringbuf_write/read`**，一次塞进/取出一整帧 14 字节 |
| 满时策略 | 只能报错拒绝 | **可选**：丢弃最新（reject）或覆盖最旧（overwrite） |
| 线程安全 | 无 | **可选锁钩子**；且 reject+SPSC 下可**完全无锁** |
| DMA 支持 | 有 `get_head_pos`/`head_pos_increment`（为 USART DMA+IDLE 设计） | 有 `ringbuf_dma_begin/commit/abort` 零拷贝路径 |

> **关键决策**：本版沿用了原实现的"head/tail 推导长度 + 牺牲一个槽位"方案，而不是用额外的 `count` 字段判满。理由见 §3.1 与 §3.6——这个选择让**单生产者/单消费者场景可以做到真正无锁**。

## 3. 设计要点

### 3.1 head/tail 推导长度（牺牲一槽）
- `head` 指向下一个可写位置，`tail` 指向下一个可读位置：
  - 空：`head == tail`
  - 满：`((head + 1) & mask) == tail`
  - 已存：`used = (head - tail) & mask`
  - 可用容量：`cap - 1`（牺牲一个槽位用于区分"空"与"满"）
- **为什么不用 `count` 字段**：`count` 虽然能存满 `cap` 字节、判空判满也直观，但 `count++`/`count--` 是非原子的读改写，且生产者与消费者**双方都会修改它**，导致同实例并发必须加锁。改用 head/tail 推导后，**生产者只写 `head`、消费者只写 `tail`**，二者不争抢同一变量——这才是成熟 FIFO 的通行做法（也是原实现的思路）。

### 3.2 容量为 2 的幂
- `ringbuf_init` 的 `cap_bytes` 必须是 2 的幂（32/64/128/256…），非 2 的幂直接返回 `RINGBUF_ERR`。
- 回绕用 `idx = (idx + 1) & (cap - 1)`，位运算替代取模，Cortex-M 上可省掉除法指令。
- **选型记得留一字节**：可用容量是 `cap - 1`。例如 MPU6050 原始帧 14 字节，想存 4 帧需要 56 字节可用 → 取 `cap = 64`（可用 63，余 7 字节）。

### 3.3 满时策略（overwrite）
- `overwrite = false`（reject）：满则返回 `RINGBUF_FULL` 拒绝，适合"丢了就丢了"的严格场景，**也是唯一能无锁使用的模式**。
- `overwrite = true`：覆盖最旧数据（推进 `tail`），适合"采集快于消费、宁可丢旧保新"的传感器流。**此模式生产者会修改 `tail`，必须加锁**（见 §4.2）。

### 3.4 两种写入路径：CPU 拷贝 vs DMA 零拷贝

**必须区分这两种情况**，因为它们的保护粒度完全不同：

| | A. CPU 拷贝路径 `ringbuf_write()` | B. DMA 零拷贝路径 `begin/commit` |
|---|---|---|
| 数据流向 | 调用方缓冲区 → CPU 拷进环形区 | DMA 直接把外设数据写进环形区 |
| 加锁范围 | **整个拷贝过程持锁** | 传输期间**不持锁**，仅 `commit` 时短暂加锁 |
| 为何如此 | 需防其他线程并发访问 | 锁管不住 DMA 这个总线主设备，持锁毫无意义 |
| 不支持 | — | 不支持 overwrite（DMA 无法在传输中途丢弃旧数据） |
| 适用场景 | 任务上下文、普通写入（默认用法） | I2C/SPI/UART 配 DMA 收数、或中断上下文收数 |

**混用保护**：DMA 在途时（`begin` 之后、`commit`/`abort` 之前）调用 `ringbuf_write()` 返回 0、`ringbuf_push()` 返回 `RINGBUF_BUSY`，由 `dma_active` 标志硬拦截，不会踩坏数据。

**回绕需分段**：`begin` 只返回**一段连续**空间（head 到缓冲区末尾）。若期望长度跨越回绕点，需两次 `begin → DMA → commit`：

```c
uint32_t cont; uint8_t *p;
p = ringbuf_dma_begin(&rb, want, &cont);   /* 第一段：buf 尾部 */
start_dma(p, cont);                        /* ... DMA 完成中断里： */
ringbuf_dma_commit(&rb, cont);
p = ringbuf_dma_begin(&rb, want - cont, &cont);  /* 第二段：buf 头部 */
start_dma(p, cont);
ringbuf_dma_commit(&rb, cont);
```

> **Cache 注意**：Cortex-M4（F411）无 D-cache，DMA 写入一致性无虞；若移植到带 D-cache 的 M7 等平台，`commit` 前需对接收区做 `SCB_InvalidateDCache_by_Addr`。

### 3.5 编译器屏障（无锁的前提）
- 无锁 SPSC 依赖"先写数据、后公开 `head`"、"先读数据、后公开 `tail`"的顺序不被编译器重排。
- 头文件提供了 `RINGBUF_BARRIER()`：GCC/armclang 用 `__asm__ volatile("" ::: "memory")`，ARMCC 用 `__schedule_barrier()`，其余为空。
- 单核 Cortex-M 为顺序执行，编译器屏障已足够（无需 DMB）。**多核或带其它总线主设备的场景，请将该宏重定义为硬件内存屏障（如 `__DMB()`）或改用锁。**

### 3.6 取舍记录：为什么选 head/tail 而不是 count

| 方案 | 可用容量 | 并发代价 |
|---|---|---|
| **head/tail 推导（本版，采用）** | `cap - 1` | 生产者只写 head、消费者只写 tail → **reject+SPSC 可完全无锁** |
| count 判满 | `cap`（多 1 字节） | 双方都改 count → 同实例并发**必须加锁** |

结论：牺牲 1 字节换来"常见单生产者单消费者场景零锁开销"，对 MPU6050 这类"一个 Handler 写、一个处理任务读"的场景更划算。

## 4. 可重入性与线程安全（回答"多线程会不会相互影响"）

### 4.1 不同实例之间：完全独立、可重入 ✅
- 中间件**没有任何 `static` / 全局变量**，所有状态都在调用方传入的 `ringbuf_t` 实例里；内部辅助函数（如 `is_power_of_two`）只使用参数，不持有状态。
- **因此：多个线程各自操作自己的 ringbuf，互不影响，也不需要任何锁。** 这是"无共享状态"设计带来的可重入性。
- **唯一例外**是日志宏 `RINGBUF_LOG_E`：默认实现为 `((void)0)`，不引入状态（可重入）。但若重定向到 `printf` / `elog` 等非可重入实现，日志本身会成为共享状态。

### 4.2 同一个实例：按模式决定是否需要锁

| 场景 | 是否需要锁 | 原因 |
|---|:---:|---|
| **reject + 单生产者/单消费者 (SPSC)** | **不需要**（`pf_lock = NULL`） | 生产者只写 `head`，消费者只写 `tail`，互不干扰 |
| reject + 多生产者 或 多消费者 | 需要 | 多个生产者争抢 `head`（或多个消费者争抢 `tail`） |
| **overwrite 模式** | **需要** | 生产者要推进 `tail` 丢弃旧数据，与消费者写 `tail` 冲突 |
| DMA 参与写入 | 需要（走 DMA 路径） | DMA 是独立总线主设备，需 `begin/commit` 协议 |

需要锁时用 `ringbuf_set_lock` 注入；它**强制校验成对**，只设其中一个会返回 `RINGBUF_ERR`（防"加锁永不解锁"的死锁）。

### 4.3 ISR 上下文的坑
- `pf_lock` 若挂的是 `taskENTER_CRITICAL` 这类**任务级**临界区，**不能**在 ISR 中调用；ISR 里应使用 `FromISR` 变体，或改用 DMA 提交路径（提交窗口极短）。
- **切勿在 ISR 中使用互斥锁**（会触发断言/崩溃）。

## 5. API 速查

| 函数 | 作用 |
|---|---|
| `ringbuf_init(rb, storage, cap)` | 用外部存储初始化（cap 须为 2 的幂，可用容量 `cap-1`） |
| `ringbuf_set_lock(rb, lock, unlock)` | 设置锁钩子（**必须成对**，否则返回 `RINGBUF_ERR`；SPSC 可留 NULL） |
| `ringbuf_is_empty / is_full` | 判空（`head==tail`）/ 判满（`(head+1)&mask==tail`） |
| `ringbuf_available` | 已存字节数 `(head-tail)&mask` |
| `ringbuf_free_space` | 剩余可写 `cap-1-used` |
| `ringbuf_capacity` | 总容量 `cap`（**注意可用为 `cap-1`**） |
| `ringbuf_push(rb, b, overwrite)` | 写 1 字节 |
| `ringbuf_write(rb, src, len, overwrite)` | **批量写（CPU 拷贝路径）** |
| `ringbuf_pop(rb, &b)` | 读 1 字节（消费） |
| `ringbuf_read(rb, dst, len)` | **批量读（消费）** |
| `ringbuf_peek(rb, dst, len)` | 窥视（不消费，**会加锁**） |
| `ringbuf_reset(rb)` | 清空 |
| `ringbuf_dma_begin(rb, want, &cont)` | DMA 预留连续可写区（返回地址或 NULL） |
| `ringbuf_dma_commit(rb, n)` | 提交 DMA 写入的 n 字节 |
| `ringbuf_dma_abort(rb)` | 放弃本次 DMA 预留（传输失败回滚） |

返回值：`RINGBUF_OK / ERR / NULL / FULL / EMPTY / BUSY`。批量接口返回**实际读写字节数**，调用方应检查是否达到预期长度。

**无效实例语义**：未 `ringbuf_init` 的实例一律表现为"容量为 0 的空缓冲"——`is_empty()=true`、`is_full()=false`、`available()=0`，任何写/读操作返回 `RINGBUF_NULL`。这样"忘记 init"会在调用点直接暴露，而不是被静默吞掉。

## 6. MPU6050 接收数据：用法示例

目标：Handler 读完 MPU6050 后把**一整帧原始数据**丢进环形缓冲；另一个任务（滤波/融合模块）取帧消费。Handler 写、处理任务读 → **典型 SPSC，可以完全不挂锁**。

```c
#include "mid_ringbuf.h"
#include "bsp_mpu6050_driver.h"   /* mpu6050_raw_data_t：14 字节原始帧 */

#define IMU_RB_CAP  64u            /* 2 的幂；可用 63 字节 = 4 帧(56B) + 余量 */

static uint8_t   g_imu_storage[IMU_RB_CAP];
static ringbuf_t g_imu_rb;

void imu_ringbuf_setup(void)
{
    ringbuf_init(&g_imu_rb, g_imu_storage, IMU_RB_CAP);
    /* 单写者(Handler) + 单读者(处理任务)、且用 reject 模式 => 无需 ringbuf_set_lock */
}

/* 生产者：Handler 读到数据后调用 */
void imu_on_data(const mpu6050_raw_data_t *raw)
{
    /* overwrite=false：保持无锁 SPSC；满了就丢最新这一帧 */
    uint32_t w = ringbuf_write(&g_imu_rb,
                               (const uint8_t *)raw, sizeof(*raw), false);
    if (w != sizeof(*raw)) {
        /* 缓冲满，本帧丢弃（可计数上报） */
    }
}

/* 消费者：滤波/融合/上报任务 */
void imu_consume_task(void)
{
    mpu6050_raw_data_t frame;
    for (;;) {
        uint32_t r = ringbuf_read(&g_imu_rb, (uint8_t *)&frame, sizeof(frame));
        if (r == sizeof(frame)) {
            /* 拿到一整帧，做滤波/姿态解算/上报…… */
        } else {
            /* 暂无整帧，vTaskDelay 一小会儿再试 */
        }
    }
}
```

> 若改用 `overwrite = true`（宁可丢旧帧也要存下最新帧），则**必须** `ringbuf_set_lock` 挂锁，因为生产者会推进 `tail`。
> 若想存物理量（`mpu6050_data_t`，7 个 float = 28 字节），把帧字节数改为 `sizeof(mpu6050_data_t)` 并调大 `IMU_RB_CAP` 即可——中间件对内容类型无感知，只认字节流。

## 7. 接入到现有 preview 驱动的建议位置

- 在 `bsp_mpu6050_handler.c` 的 `imu_handler_thread` 里，读到 `mpu6050_raw_data_t` 后（现代码直接走 `event.pf_callback`），可改为**先 `ringbuf_write` 进缓冲、再触发回调/通知消费者**，把"采样"与"处理"解耦。
- 缓冲实例建议挂在 `bsp_imu_handler_t` 里（`ringbuf_t fifo;` + 一块 `uint8_t fifo_buf[]`），由 Handler 在 `bsp_mpu6050_handler_inst` 时 `ringbuf_init`。这样与现有桥接结构一致，且不破坏 driver 层的纯协议特性。
- 因 Handler 单写、处理任务单读，默认**不用挂锁**；只有引入第二个写者或启用 overwrite 时才加。

## 8. 注意事项 / 常见坑

1. **可用容量是 `cap - 1`**：选型时记得留这一字节。想存 N 帧 × 14 字节，请保证 `cap - 1 >= N × 14`。
2. **容量必须是 2 的幂**，否则 `init` 直接失败；不要传 10/100 这种值。
3. **存储区生命周期**：`ringbuf_init` 不复制数据，只保存指针；传局部数组会悬空。用 `static`/全局数组。
4. **整帧读写对齐**（重要）：字节粒度缓冲，若消费者某次只读了部分字节（不足一整帧），**后续帧边界会永久错位**。务必像 §6 那样"凑够一整帧才取"。
5. **overwrite 必须加锁**：它会推进 `tail`，与消费者冲突；只有 reject 模式才能无锁。
6. **锁必须成对**：`ringbuf_set_lock` 会拒绝只设其一的配法；且两者语义要一致（同一把锁/同一临界区）。
7. **批量接口检查返回值**：`ringbuf_read` 返回实际读出字节数，不足一整帧时不要当整帧用。
8. **peek 会加锁**：虽不消费数据，但为防撕裂会加锁；若你的锁不可重入，不要在持锁上下文里嵌套调用。
9. **批量写勿用临界区**：`ringbuf_write` 整段持锁逐字节拷贝，若 `pf_lock` 是临界区（关中断）且 `len` 较大，会长时间关中断。批量写建议挂互斥锁；DMA 路径不受此影响。
10. **DMA 与 CPU 不可混用**：DMA 在途时 CPU 写入被拦截（返回 0 / `RINGBUF_BUSY`），这是保护而非错误。
11. **ISR 中禁用互斥锁**，且不要用任务级临界区钩子（见 §4.3）。
12. **多核平台需重定义 `RINGBUF_BARRIER()`** 为硬件内存屏障，否则无锁 SPSC 不成立。

## 10. 自测覆盖

本地（PC + gcc）已验证，全部通过：

- 容量语义（`capacity=8` / 可用 7）、写满 7 被拒第 8 字节、读写一致
- overwrite 保留最新 7 字节、跨边界回绕（200 次）、无锁 SPSC 路径（不挂锁）
- `set_lock` 成对校验（4 种组合）
- 无效实例语义（未 init 时的正确返回）
- DMA：预留/提交/回滚、回绕分段（两段顺序正确）、DMA 在途拦截 CPU 写入、未 begin 就 commit 报错
- peek 不消费（带锁路径）

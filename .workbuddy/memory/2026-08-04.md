# 2026-08-04 工作日志

## LED 桥接模式驱动 bug 排查（BSP/LED + System/OSAL）

排查了 LED 桥接模式（bsp_led_driver.c / bsp_led_handler.c）的实际 bug，结论：设计文档
`LED_BSP_桥接模式方案说明.md` 已过时——桥接代码确实已落地并接线，但存在多个运行期缺陷。

关键发现（按严重度）：
- **运行期失效**：`Test_3()`（FreeRTOS_tasks.c，被 idle_task@prio1 调用）结尾 `while(1);`
  忙等，饿死优先级 0 的 handler_thread → 队列里的 blink 事件永远不被处理，LED 不闪。
- **接到空操作桩**：FreeRTOS_tasks.c 里的 `led_on/off_myown` 只 printf 不碰 GPIOC；
  真正驱动 GPIO 的版本在 system_adaption.c，但因 `system_init_resources()` 无人调用被
  `--gc-sections` 回收，桥接实际连的是空桩。
- **重复全局符号隐患**：`led_on_myown`/`led_off_myown`/`led_operations_myown` 在两文件各定义
  一份（一份只打印、一份驱动 GPIO）。当前靠 gc-sections 才链接过；一旦调用
  `system_init_resources()` 即 multiple-definition 链接失败。
- `bsp_led_driver_t.pf_led_countroler` 在 OS_SUPPORTING 下从不赋值（仅 `#ifndef` 分支设），
  driver.c 的 `led_blink`/`led_control` 也被 `#ifndef OS_SUPPORTING` 排除 → 实现层被掏空，
  blink 逻辑被 handler 重复实现（桥接分层倒置）。
- `handler_led_control` 用 `index <= MAX_INSTANCE_NUMBER` 越界（应为 `<`）；
  `led_index_t` 的 `LED_NOT_INITIALIZED=0xFFFFFFFF` 超出 enum 底层 int 范围（非可移植）。
- `__event_process` 首个 index 检查 `|| LED_NOT_INITIALIZED` 自相矛盾（下一行又拒绝它）。
- Test_3 的局部 `handler_1/led1` 未零初始化，`is_inited` 读栈垃圾（UB，靠运气为0）。
- blink 用 `delay_ms(1)` ×(cycle×times) 循环切 GPIO，占住整条 handler 线程 → 多灯只能串行。
  （**更正**：`p_os_time_delay->delay_ms` 走 OSAL → `osal_freertos.c:33 vTaskDelay`，是**阻塞
  让出**而非忙等，不烧 CPU；问题只是线程被独占 + init 里还有 `delay_ms(600)` 阻塞。）

注：legacy `bsp_led.c` 仍编入（led_task 空转、LED_BLINK_3_TIMES 用 vTaskDelay 阻塞），
但 app_task_create 里 led_blink_task 已注释，桥接路径才是当前实际跑的。

## 任务优先级规约（本工程 FreeRTOS）

`configMAX_PRIORITIES=5` → 合法 0..4；**FreeRTOS 0 是最低**（tasks.c:372），
`configTIMER_TASK_PRIORITY=2`，`configUSE_PREEMPTION=1`，`configIDLE_SHOULD_YIELD=1`，
`configUSE_TIME_SLICING` 未定义 → 默认 1（同级 1ms 轮转）。
OSAL `osal_freertos_thread_create` 直传 priority 给 xTaskCreate，**不做反转**，语义同 FreeRTOS。

| prio | 占用 |
|---|---|
| 0 | FreeRTOS Idle（保留，勿给功能任务）；**当前 handler_thread 误设于此** |
| 1 | 用户 idle_task；led_blink_task(已注释) → **LED handler 应放这里** |
| 2 | ota_task、Timer daemon |
| 3 / 4 | uart_driver / usart1_parse（当前未启用） |

**结论：`handler_thread` 优先级应为 1**（FreeRTOS_tasks.c:233 的 `0` 要改）。理由：必须 ≥1 才脱离
Idle 级；必须 <2 以免抢占 OTA（Ymodem 有超时约束）和定时器守护任务。

**⚠️ 文档错误待修**：`docs/架构与调用逻辑说明.md:105` 写"优先级数字越小越高（FreeRTOS：0 最高）"
——反了，FreeRTOS 是 0 最低。疑似当初把 handler 设成 0 的根因。

## 时钟使能归属规范调研（未改代码）

**结论**：时钟使能按"资源归属"分层，禁止全塞 gpio.c，也禁止模块隐式依赖调用者开钟。
- PLL/HSE/SYSCLK/总线分频/Flash 等待 → `SystemClock_Config()` 唯一一处
- GPIOx 端口 AHB1 时钟 → 与引脚配置同层（写 `GPIO_Init` 的那个函数）
- 外设时钟（SPI1/USART1/TIM2/ADC1/I2C2/DMA2/SYSCFG）→ 各自 init 内
- **硬规则**：使能时钟那行必须是第一个写该模块寄存器的语句，且与后续配置在同一函数体内、中间不跨模块调用。

**大厂依据**：
- AUTOSAR `SWS_MCUDriver` R19-11：`SWS_Mcu_00116`（单一用途寄存器→实现该功能的驱动）、`SWS_Mcu_00244`（影响多模块且是 I/O 寄存器→PORT 驱动）、`SWS_Mcu_00245`（影响多模块且非 I/O→MCU 驱动）。启动序 `Mcu_Init → Mcu_InitClock → Mcu_DistributePllClock → Port_Init → Dio_Init`。
- ST CubeMX / NXP MCUXpresso：`MX_GPIO_Init` 只管引脚+端口时钟，`MX_USART1_Init` 只开 USART1 时钟。
- Linux/Zephyr：设备树声明 + probe 内 `devm_clk_get/clk_prepare_enable` + pinctrl 子系统，**不存在全局 gpio.c 角色**；原因是模块有独立生命周期，全局初始化会破坏卸载/复用。

**本项目实查问题（待处理，用户要求先不改代码）**：
1. `Core/Src/spi.c:24` `cs_io_init()` 在 `spi.c:32` 使能 GPIOA 时钟**之前**调用 → PA4（W25Q64 CS）MODER 写入不生效，时序 bug。
2. `cs_io_init()` 自身不开 GPIOA 时钟 → 隐式前置条件，不可独立复用。
3. 仅 `BSP/ADC/bsp_adc.c:10/71/73` 自己开 DMA2/GPIOA/ADC1，是唯一符合规范的 BSP 模块。
4. `bsp_w25qxx` / `bsp_aht21` / `AT24Cxx` / `LCD` 全不开时钟，依赖 `main()` 里 `spi1_init()`/`hardware_iic_init()` 的调用顺序 → 单独用即死。
5. `gpio.c` 职责混杂：NVIC 优先级分组（系统级）+ led/key/mpu_int 引脚；而 SPI/IIC/USART 引脚分散在 `spi.c`/`iic.c`/`usart.c` → 引脚层被拆成两处。
6. `gpio.c:12` `led_init()` 被注释，但 `FreeRTOS_tasks.c:214` 直接 `GPIO_ResetBits(GPIOC, Pin_13)` → GPIOC 时钟可能从未使能。
7. 重复开钟：`iic.c` 的 GPIOB 在 line 22/662/722/793/840 各开一次；`usart.c` 存在 `USART1_Config()` 与 `ota_usart1_config()` 两套各开一遍 GPIOA/USART1/DMA2；`gpio.c:52` 与 `:77` 重复开 SYSCFG。（位操作幂等，仅浪费指令，不算 bug，但说明缺单一 owner。）

**给项目的建议（未执行）**：短期采用"每个写 `GPIO_Init` 的函数自开本端口时钟"（改动小、立即消除隐患），不做引用计数/不做 `bsp_clock.c`（过度设计）。中期若板子定型，可把全部引脚配置归拢到 `gpio.c` 的 `board_pins_init()`，`spi1_init` 只保留 SPI1 时钟+参数。

## MPU6050 只读到一帧数据的定位（只分析，未改代码）

**结论**：数据链完整跑通一次（temp 28.93℃、ax 0.018g、az 1.267、gx -0.427dps，数值自洽、是真实采样）。
只读一次的直接原因：`dma_interrupt_callback`（driver.c:1439）在 DMA1_Stream2 中断里重开 DATA_RDY
（写 INT_EN=0x01）失败，`ret=255`（即 iic_mem_write 返回 -1）；而 `int_interrupt_callback`(driver.c:1352)
已先写 `COLOSE_ALL=0x00` 关掉全部中断 → INT 引脚此后无脉冲 → EXTI 不再触发。**该处无任何重试/兜底**。

**三条日志真伪**（同源于返回值约定 0/1 不统一）：
- `read accel data error ret=0` = 假警报：`iic_mem_read_dma` 成功返回 0（iic.c:1284），驱动按 1=成功判（driver.c:1388）。
- `queue put failed` = 假警报：`osal_freertos_queue_put` 成功返回 OSAL_OK=0（osal_freertos.c:97），handler 按 !=1 判（handler.c:332）。
- `ret=255` = 真失败，唯一真 bug 点。

**其他待修（本轮发现）**：
- EXTI 配 Falling（gpio.c:91），MPU 配 ACTL=1 高有效 + LATCH=0（50µs 脉冲，driver.c:774 写 0x90）→ 能进但语义拧着（上升沿事件、下降沿触发，延迟 50µs）。
- ISR 内做阻塞式 I2C 写（mpu_write_reg 多条 return -1：i2c_wait_idle/EV5/EV6/EV8_2）+ ISR 内调 log_i（elog 有锁）→ 脆弱；重开中断应移到任务上下文。
- `unpack_task` az 除数用 14418（FreeRTOS_tasks.c:402），x/y 用 16384，三轴标度不一致。
- 环形缓冲无"空"判断，`queue_get` 失败仍继续读 → 样本一多会打印陈旧数据。

## 20:54 复测（返回值约定已修）：仍是"只读一帧"，剩余真因分析

改动确认：`iic_mem_read_dma` 改返回 1（iic.c:1284）、`dma_interrupt_callback` 用 `int8_t ret`（driver.c:1418）
→ 上一轮那两条假警报消失，日志只剩 `write MPU_INT_EN_REG error, ret = -1`（driver.c:289）。

**定位方向**（未改代码）：DMA 读的终止握手不完整。`DMA1_Stream2_IRQHandler`（iic.c:1290-1308）在 TC 里只做
`DMA_Cmd(DISABLE) + I2C_DMACmd(DISABLE) + I2C_AcknowledgeConfig(ENABLE)`，然后立刻在 ISR 里发起 `mpu_write_reg`。
对比 HAL `I2C_MasterRxCplt`：应 `CR2&=~LAST`、`CR2&=~DMAEN`、`CR1&=~ACK`、等 BTF、再**软件发 STOP**、确认 BUSY=0。
当前实现把 ACK 反向置 1、从不清 LAST、不等 BTF、不软件补 STOP、不校验 BUSY → 极可能 STOP 未生效/从机仍处发送态，
BUSY 恒 1 → `mpu_write_reg` 第一步 `i2c_wait_idle()` 超时 → -1。这也能解释"之后永久死"。
**可证伪实验（一次下载即可）**：把重开 INT_EN 挪到 handler 线程里延后 5ms 做 —— 仍 -1 ⇒ 总线锁死(BUSY 恒1)；
成功 ⇒ 只是"TC 里立刻写"的时序竞争。

**改动清单（待用户确认再落地）**：① TC ISR 补齐终止握手/校验 BUSY，失败走 `hw_iic_bus_reset`(9 SCL+STOP+重init)；
② INT_EN 重开移出 ISR，任务上下文 + 重试；③ 更彻底：INT_EN 常开（脉冲模式 + 读 INT_STATUS 自动清），删掉"关-开"周期；
④ `mpu_write_reg` 失败分支返回不同负码(-1..-4)便于定位；⑤ 顺带修 az 除数、环形缓冲空判断。

## 21:40 交付修改方案（代码给用户自己改，未落地）

方案定稿为"INT_EN 常开 + ISR 只做 DMA 读 + DMA 收尾补全 + 任务侧自愈看门狗"，共 4 个文件 6 处：
- `iic.c`：新增 `s_bus_fault` 标志、`iic_bus_recover()`（I2C_DeInit→PB10/PB3 开漏→9 个 SCL 脉冲→手动 STOP→`hardware_iic_init()`）、
  `iic_dma_read_busy()`/`iic_take_bus_fault()`；重写 `DMA1_Stream2_IRQHandler` TC 分支：
  停流 → **清 LAST** → 关 DMAEN → **关 ACK** → **软件 GenerateSTOP** → 等 BUSY 清零(超时置故障) → 清 AF → 恢复 ACK → 回调。
- `iic.h`：三个新原型。
- `driver.c`：`int_interrupt_callback` 删掉写 `COLOSE_ALL` 和重开逻辑，只在入口 `if (iic_dma_read_busy()) return;`；
  新增 `mpuxxx_reopen_data_ready()` 供恢复路径用。
- `handler.c`：循环里加 `MPUXXX_RECOVER_IDLE_MS=200` 看门狗 + `iic_take_bus_fault()` → `iic_bus_recover()` + 重开 INT_EN。
- 小修：`FreeRTOS_tasks.c:402` az 除数 14418→16384；`:386` `ret == 1` → `ret == 0`（OSAL_OK）。
另附最小改动替代方案 B（保留关-开语义，把重开挪到 handler 线程重试，代价是牺牲部分采样率）。

## 23:06 实锤：BUSY 恒 1（ret = -2），根因确认

用户按建议给 `mpu_write_reg` 加了分级负码（iic.c:892=-1 入参 / **897=-2 `i2c_wait_idle` 超时** / 905=-3 EV5 / 913=-4 EV6 / 921=-5 寄存器字节 EV8_2 / 931=-6 数据字节），
新日志 `write MPU_INT_EN_REG error, ret = -2` → **总线 BUSY 恒 1，被上一次 DMA 读锁死**。

**机理**：`DMA1_Stream2_IRQHandler` 的 TC 分支里 `I2C_AcknowledgeConfig(I2C2, ENABLE)`，
等于在最后一字节之后又允许主机继续 ACK 第 15 字节；DMA 已关、RXNE 没人清，从机持续送数据 → 总线上永远有字节在跑 → STOP 永不产生 → BUSY 恒 1。
所以：(a) 读到的 14 字节数据是好的；(b) 后续任何 I2C 事务在第 1 步就死；(c) **方案 B（把重开挪到任务里延后）无效**，BUSY 不会自愈。

**最小修复（只改 DMA TC 收尾，约 6 行）**：`DMA_Cmd(DISABLE)` → `I2C_DMALastTransferCmd(DISABLE)` → `I2C_DMACmd(DISABLE)` →
**`I2C_AcknowledgeConfig(DISABLE)` + `I2C_GenerateSTOP(ENABLE)`** → 等 BUSY 清零（超时打 `log_e("bus busy stuck")`）→ 清 AF → 恢复 ACK。
这正是 HAL `I2C_MasterRxCplt` 的顺序。若加了之后仍打印 busy stuck，说明从机拉住 SDA，才需要 9 SCL 解锁函数。

## 23:11 修复生效，暴露第二层问题（日志饱和 / FIFO / 关-开INT_EN）

**已解决**：DMA TC 收尾 6 行（清 LAST + 关 ACK + 软件 STOP + 等 BUSY）之后，`-2` 与 `open interrupt error` 消失，
数据连续输出，wbuffer 每次 +14。**总线锁死根因确认（ACK 被重新置 1 → 主机继续收第 15 字节 → STOP 永不产生）。**

**新暴露问题**：
1. **日志饱和（P1）**：每个采样周期两个回调共打 12 行 ≈ 500 字节，115200 下约 43 ms > 26 ms 采样周期(38.5Hz)
   → 串口饱和，行被截断（`unpack_task: addr = 0`、`x_set_inter...` 半截），长 ISR 还会丢 tick，时间戳不可信。
   `DEBUG` 来自 CMake `$<$<CONFIG:Debug>:DEBUG>`（不是 bsp_config.h）。ISR 里 printf 必须禁掉。
2. **INT_STATUS 恒 0x11**（bit4 FIFO_OFLOW 常驻）：FIFO 开着但从未被读走 → 应注释掉 `mpuxxx_fifo_init` 调用。
3. 仍在做"关 INT_EN / DMA 回调里重开"（每帧两次 I2C 写 ≈0.4ms，且是"重开瞬间重触发"的入口）→ 可整段删除，INT_EN 保持 0x01。

**判据**：清理日志后看时间戳应稳定 ~26ms/帧（SMPLRT_DIV=25 + DLPF=4 → 1kHz/26=38.5Hz）。
若仍是 3~5ms/帧，说明 DLPF 没生效（8kHz/26=307Hz），查 0x1A 的 DLPF_CFG。

## 21:45 逐帧梳理 I2C 通信全过程（文档产出，仍未改代码）

产出 `docs/MPU6050_I2C通信全过程梳理.md`：把这段启动日志还原成 **I2C2 上 19 次事务**
（16 写 + 2 单字节读 + 1 次 14 字节 DMA 读），逐帧给出 reg/data/日志锚点，第 19 帧（0x38←0x01）失败后彻底静默。
- 初始化 15 帧：0x6B=0x80 → 0x6B=0x00 → 0x1B=0x18 → 0x1C=0x00 → 0x19=0x19 → 0x1A=0x04 → 0x38=0x01 → 读 0x75=0x68
  → 0x6B=0x01 → 0x6C=0x00 → 0x6A=0x04 → 0x23=0x78 → 0x6A=0x40 → 0x37=0x90 → 0x38=0x10。
- 中断 4 帧：0x38=0x00 → 读 0x3A=0x15 → DMA 读 0x3B×14 → 0x38=0x01（失败）。
- `0x15` 解码 = DATA_RDY | PLL_RDY | **FIFO_OFLOW** → 真正触发引脚中断的是 FIFO 溢出（INT_EN 当时只有 0x10）。
  与 FIFO 容量自洽：1024B / 12B = 85 包 ÷ 38.5 Hz ≈ 2.2 s ≈ 日志 tick 2436 ms。
- **新结论：两个时间戳都是 2436 不是"测得准"，而是 SysTick 被饿死**。SysTick/PendSV 是最低优先级 15，
  EXTI9_5 与 DMA1_Stream2 都是 5；`DEBUG_OUT = printf` 走 USART1 115200 忙等，一行 35~49 字符 ≈ 3~4 ms，
  `int_interrupt_callback` 内含 5~6 条打印 → 整个 ISR 约 20 ms，期间 tick 不走。**该时间戳不能用来测 DMA 耗时。**
- 顺带核实：`0x37=0x90` 是 INT_LEVEL=1（低有效）+ INT_RD_CLEAR=1，配 EXTI 下降沿是**对的**
  （推翻 09:00 那条"上升沿事件配下降沿触发"的判断）；`SMPLRT_DIV=0x19`(25) 实际 38.5 Hz 而非日志的 "50Hz"。

## 22:20 追问：`0x15` 的 FIFO_OFLOW 有问题吗

**结论：必然溢出，不是偶发故障——FIFO 开了但从未被读。**
- 算账：`0x23=0x78` = ACCEL+3 陀螺 = **12 B/样本**（TEMP_FIFO_EN(0x80) 没开，不是 14 B）；ODR 38.46 Hz
  → 461 B/s → 1024B ÷ 461 ≈ **2.22 s**，与日志首次中断 tick 2436 ms（减 init 前 ~200 ms）完全吻合。
- 中断里 `iic_mem_read_dma(0x3B,14)` 读的是**传感器寄存器组**，不是 `FIFO_RW(0x74)`；FIFO_COUNT 也从未读。
  ⇒ FIFO 实际只当"2.2 s 定时器"，85 包数据全废。这也旁证了"读寄存器而非读 FIFO"（读 14B 含温度，与 12B 包长不符）。
- **datasheet 原文**（RM-MPU-6000A-00 §4.31）：溢出后 "oldest data will be lost and new data will be written"，
  即**滚动覆盖最旧字节**，`FIFO_COUNT` 饱和在 1024；按字节滚导致**包边界错位**，之后读 FIFO_RW 不再对齐，必须 FIFO_RESET。
- 危害：① 0x3B 影子寄存器仍更新，所以数据看着对（易误判）；② 溢出周期依赖 1024/12/ODR，改配置就漂，2.2s 是巧合；
  ③ FIFO 永远停在满状态，INT_STATUS.bit4 常为 1，若 INT_EN 常开且顺手使能 FIFO_OFLOW → 中断风暴。
- 改法 A（推荐）：`0x23←0x00` + 清 FIFO_EN，只留 DATA_RDY(0x01)，中断读 0x3B 14B。
  改法 B（真用 FIFO）：先读 0x72 再读 0x73（顺序不能反）→ count/12 整包 burst 读 0x74，余数丢弃，仅 overflow 时 FIFO_RESET。
- 补充：INT_STATUS 的 bit0 DATA_RDY / bit2 PLL_RDY 是**状态位，不受 INT_EN 影响**，0x15 只说明读的瞬间三个标志都为 1，
  不代表三种中断同时触发。已把本节作为 §5.1 补进 `docs/MPU6050_I2C通信全过程梳理.md`。

## 22:26 追问：FIFO 是不是只用来触发首帧

**判断：意图对（FIFO 只当节拍源），但 FIFO 不能当节拍源。**
- "只触发一次"是第 19 帧失败后 `INT_EN=0x00` 的**假象**，不是设计。
- `FIFO_OFLOW` 是"缓冲满了"的告警，非周期信号；满后停在满态滚动覆盖，要拿下一个 2.2 s 节拍必须 `FIFO_RESET`
  清指针。不 reset 则读走 INT_STATUS 后要么随每次写入反复置位（≈26 ms 风暴），要么从此安静 —— 都不是"每 2.2 s 一帧"。
- 数据通路走 0x3B 本身正确，但它是"最新一帧快照"、不排队无时间戳，两次读之间样本丢弃；
  38.5 Hz = 26 ms 预算，而每条中断含 2 写 + 1 读 + 1 DMA + printf(3~4 ms/行)，实际跟不上。
- **定论（待落地）**：FIFO 彻底关 —— `0x6A←0x04` 复位一次 → `0x23←0x00` → `0x6A←0x00`；
  节拍源改 `0x38←0x01`（DATA_RDY）；不再在 ISR 里开关 INT_EN（脉冲模式 + 读状态自清）。
  这样才真正"一帧一中断一读"，且彻底消掉溢出源。已补进文档 §5.1。

## MPU6050 + VOFA+ 姿态可视化方案设计（初版方案）

用户已能通过串口连续输出 MPU6050 数据，提出要用 VOFA+ 可视化板子角度与姿态。
本轮只做了诊断 + 设计方案 + 代码草案，**未改动任何工程文件**（遵循"先诊断 → 改动清单 → 逐条请求修改"的协作节奏）。

### 摸清的事实（读代码得出，后续别重新查）
- MPU6050 配置：`bsp_mpu6050_driver.c:1209` SMPLRT_DIV=0x19 → **50Hz 采样**；DLPF=0x04（25Hz）；accel ±2g（16384 LSB/g）；gyro ±250dps（131 LSB/dps）；DATA_RDY 中断使能。
- 串口：USART1，**115200**（`Core/Src/usart.c:221`）。已有 `usart1_transmit(uint8_t*, uint16_t)` 阻塞整块发送函数（usart.c:397），可直接喂 VOFA 帧。
- FreeRTOS tick = **1000Hz**（`OS/FreeRTOSConfig.h:60`），`osal_time_base_freertos.get_tick_ms()` 分辨率 1ms，够算 dt。
- CMake：`cmake/stm32cubemx/CMakeLists.txt` 是**显式源文件列表**（非 GLOB），新增 .c 必须手工加。
- `TOOLCHAIN_LINK_LIBRARIES = "m"` 已链接 libm，`atan2f/sqrtf` 可直接用。
- FPU 硬浮点：`-mfpu=fpv4-sp-d16 -mfloat-abi=hard`，`--specs=nano.specs -u _printf_float`（所以 %f 可用）。
- 中断：`EXTI9_5_IRQHandler` 在 `FreeRTOS_tasks.c:466`，回调 `pf_pin_interrupt_callback`。
- 链路：driver 写 `circular_buf`(深10) → `handler_instance.p_unpack_queue_handle` 放 token → `unpack_task` 取 token 后读 `circular_buf.pf_get_rbuffer_addr()` 解包。

### 结论（已给出）
1. 协议选 **JustFloat**（6 通道 28B/帧，50Hz 仅 1.4KB/s，115200 下占 12%）。核心理由不是带宽，而是**帧尾 0x00 0x00 0x80 0x7F 是自同步标记**，串口丢字节后能自动重新对齐；FireWater 靠 `\n`，一旦和 elog 输出混流就永久错位。
2. 算法先上**一阶互补滤波**（accel 低通 + gyro 高通，τ=0.5s → @50Hz k≈0.96），30 行搞定；后续可升级 Mahony（四元数，VOFA+ cube 支持四元数模式）。F411 有 FPU，Mahony 算得动。
3. **绝不能用 `log_i` 发 VOFA 数据**——elog 会加 `[时间] I tag:` 前缀，文本协议必炸。

### 指出必须修的 3 个坑
1. `FreeRTOS_tasks.c:402` `az = accel_z_raw / 14418.0` **单位错**，±2g 满量程是 16384。导致 az 静态显示 1.136g，pitch/roll 全错。
2. **陀螺零偏未标定**。MPU6050 静止零偏 ±1~3dps，积分即漂 1~3°/s。必须上电静止采 500 帧求均值。
3. dt 不能用固定 20ms 蒙，handler 是 `delay_ms(1)` 轮询 + 队列，到达有抖动 → 用 tick 实测并 clamp。

另注：`mpuxxx_data_t` 的 ax/ay/az/gx/gy/gz 是 **double**，M4F 上 double 是软件模拟，比 float 慢约一个量级；50Hz 下不致命但不该这么写，建议热路径用 float 局部变量绕开。

### 计划中的文件改动（待用户确认后落地）
- 新增 `BSP/MPU6050/bsp_mpu6050_attitude.c/h`（guard `BSP_MPU6050_ATTITUDE_H`）：纯算法，`att_init/att_calib_gyro/att_update`，不依赖硬件。
- 新增 `BSP/USART/bsp_vofa.c/h`（guard `BSP_VOFA_H`）：`vofa_send_floats(const float*, uint8_t)`，只依赖 `usart1_transmit`，设备无关可复用于 FOC 调参。
- 改 `unpack_task()`：解包 float → dt → 标定 → 解算 → 组帧 6 通道（I0..I2 欧拉角，I3..I5 加速度）。
- 改 `cmake/stm32cubemx/CMakeLists.txt`：`MX_Application_Src` 加两行。

### 需要向用户强调的物理限制
6 轴（无磁力计）**yaw 必然漂移**，这是原理限制不是 bug。VOFA+ cube 转久了会歪属于正常，roll/pitch 因为有重力矢量校正不会漂。

## 追加：卡尔曼滤波教学 + 仿真基线（用户问"详细讲解数据处理中的卡尔曼滤波"）

讲解围绕他现有互补滤波展开，未改任何代码。核心论点：**卡尔曼在 6 轴 IMU 上的真正价值是隐式陀螺零偏估计器，不是"更准"**。

### 仿真基线（50Hz / 6s / 陀螺残余零偏 0.6dps / 加计噪声 σ=2.5°，R 按 σ²=6.25 匹配）
| 方案 | RMS 误差 |
|---|---|
| 陀螺纯积分 | 2.44°（6s 漂 +3.60°）|
| 加速度计直接算角 | 2.48° |
| 一维卡尔曼 | **0.48°** |

- 稳态卡尔曼增益 K≈0.043，对应互补滤波 α=1-K=0.957 → **与他现在用的 α=0.96 几乎等价**，这就是"换了卡尔曼感觉没区别"的原因。
- 零偏估计：6 秒只收敛到 0.500（真值 0.6），收敛慢于固定标定。**卡尔曼换掉的是"上电静止标定"，不是"不需要标定"**。
- R 调小到 0.5 → RMS 0.76°（噪声大）；R 调到 100 → RMS 0.55°、K 掉到 0.015（跟得慢）。

### 两个必须记住的实现坑
1. **Q/R 量纲是"角度²"**。Lauszus 那套经典值（Q_angle=0.001, Q_bias=0.003, R=0.03）是**弧度**版。若用度，必须 ×(180/π)²=3283，即 R≈98。成套抄错会让 K 变成 0.99（完全跟加计噪声）或 0.0003（退回纯积分）。
2. Lauszus 流行实现的协方差更新 `P[1][0] -= K1*P[0][0]` 用的是**已被更新过的** P[0][0]（原地改），数学上不严格。正确做法是先保存旧 p00/p01。

### 结论（已告知用户）
手表项目要全姿态应选 **Mahony**（四元数、参数少、互补结构），不要上 EKF（15 状态是无人机导航用的）。3 轴独立卡尔曼在 pitch 接近 ±90° 会退化，且 yaw 依然无解。

## 追加：卡尔曼 vs 互补滤波的实测开销（反汇编统计，未改工程）

用工程同款工具链 `/opt/ST/STM32CubeCLT_1.21.0/GNU-tools-for-STM32/bin/arm-none-eabi-gcc`
（`-mcpu=cortex-m4 -mfpu=fpv4-sp-d16 -mfloat-abi=hard`）编译后 objdump 统计，按 Cortex-M4F 周期表折算 @100MHz：

| 实现 | -O0 周期 | -O0 µs | -Os 周期 | -Os µs |
|---|---|---|---|---|
| 卡尔曼核心（每轴） | 285 | 2.85 | 81 | 0.81 |
| 卡尔曼 + `1/S` 合并（每轴） | 274 | 2.74 | 70 | 0.70 |
| 互补融合核心（每轴） | 124 | 1.24 | 58 | 0.58 |
| `__ieee754_atan2f` | 206 | 2.06 | — | — |
| `sqrtf` | 44 | 0.44 | — | — |

**单帧（2 轴）总账**：现有 att_update 含被调函数 ≈ 849 周期 / 8.5µs（-O0）。
换成 2 轴卡尔曼 ≈ 1171 周期 / 11.7µs，**增量仅 +3.2µs（-O0）或 +0.46µs（-Os）**。

**结论：算力完全不是瓶颈。** 单帧各环节耗时排序（真实差距）：
1. `printf` 23 字节 @115200 ≈ **2000 µs**（阻塞在同一任务里）
2. I2C 14 字节 @100kHz ≈ 1560 µs（DMA 总线）/ ISR 寄存器操作 ≈ 1050 µs
3. `atan2f` ×2 ≈ 412 周期... 实际 412 个周期数写错了，应为 2×206 周期 ≈ 4.1µs
4. 滤波整体 ≈ 8.5 µs
5. 卡尔曼相对互补的增量 ≈ 3.2 µs

即 **printf 是滤波开销的 235 倍**。采样率提到 1kHz 时卡尔曼增量也只占 0.32% CPU。
真正会"跟不上"的唯一场景：采样周期小于 printf 的 2ms（即 >500Hz），届时该动的是 UART 发送方式，不是滤波器。

另：Debug 构建是 `-O0`（CMAKE_C_FLAGS_DEBUG="-O0 -g3"），Release 才是 `-Os`；-O0 下滤波器慢 3.5 倍。
栈：`unpack_task` 静态 96B / 任务栈 4KB，`att_update` 80B，加两个卡尔曼实例（约 72B）无压力。

## 【已确认 BUG】陀螺量程与换算系数不匹配 → 三轴角速度全部 8 倍偏小（yaw 尤其明显）

用户报"绕 Z 轴转动这项数据一直不准"。对手册 PS-MPU-6000A-00 Rev3.4 §6.1 核实后确认根因：

- 手册：FS_SEL=0→±250°/s→**131** LSB/(°/s)；1→±500→65.5；2→±1000→32.8；**3→±2000→16.4**
- 代码 `bsp_mpu6050_driver.c:1183` 写的是 `FS_SEL_BIT(0x03)`，宏 `FS_SEL_BIT(x)=(x<<3)` → 写寄存器 0x18 → **实际量程 ±2000 dps，灵敏度 16.4**
- 但 `unpack_task` 里除以 **131.0**（±250 的系数）
- 比值 131/16.4 = **7.988 ≈ 8**，读数只有真值的 12.5%

**为什么只有 yaw 明显**：roll/pitch 有加速度计绝对校正（重力矢量）兜底，最终值仍正确，只是动态响应慢 8 倍；yaw 无参考、纯积分 → 直接小 8 倍。转 90° 只显示约 **11.3°**。

**叠加因素**：`ATT_GYRO_DEADBAND_DPS=0.20` 作用在已衰减 8 倍的信号上 → 真实 1.6dps 的转动测得 0.2dps，正好落在死区 → **慢转时 yaw 完全不动**。

### 第二处 bug（驱动层，同源）
`mpuxxx_set_gyro_fsr(p, fsr)` 收到的 `fsr` 是**移位后的寄存器值**（0x18），但内部 `switch (fsr) { case 0x00..0x03 }` 比较的是**未移位的 FS_SEL 码** → 永远走 `default: gyro_scale = 131.0`。
`mpuxxx_set_accel_fsr` 同样问题：`AFS_SEL_BIT(0x01)=0x08` 会落到 default 得 16384（应为 8192）。当前 ±2g 恰好因为 `AFS_SEL_BIT(0x00)=0x00` 与 `case 0x00` 撞上而"看起来正确"。
影响：所有走 `pf_get_*` 的驱动内解码路径（driver.c:618/722/887/974/1064 等）的 gx/gy/gz 都偏小 8 倍。

### 修复方案（待用户确认，未改代码）
- A 最小改动：把 `MPU_GYRO_LSB_PER_DPS` 与驱动 `gyro_scale` 的 131.0 改为 **16.4**，保留 ±2000
- B 推荐：量程改 ±500（`FS_SEL_BIT(0x01)` → 65.5）或 ±250（131），兼顾分辨率
  分辨率：±2000→0.061°/s/LSB，±500→0.0153，±250→0.0076
- 两案都必须同时修 `set_gyro_fsr` / `set_accel_fsr` 的 switch（改用 `fsr >> 3` 判断）

### 已核实无误的部分
- 寄存器地址：0x3B 起 14 字节 = ACCEL(6)+TEMP(2)+GYRO(6)，与 RM-MPU-6000A-00 一致
- 16 位大端补码解码 `(int16_t)((uint16_t)h << 8 | l)` 正确
- 温度公式 `36.53 + TEMP/340` 与手册一致
- 加速度 ±2g / 16384 一致
- 手册明确 burst read 保证同一采样时刻，当前 DMA 连读 14 字节的做法正确

### ✅ 已应用修复（用户选方案 A，2026-10-18 18:26）
共 4 处，编译通过（FLASH 68948B / 15.03%，较改前 +40B）：
1. `Core/Src/FreeRTOS_tasks.c:379` `MPU_GYRO_LSB_PER_DPS` 131.0f → **16.4f**
2. `BSP/MPU6050/bsp_mpu6050_driver.c:15` `gyro_scale` 初值 131.0 → **16.4**
3. `driver.c:130` gyro switch → `switch ((fsr >> 3) & 0x03U)`
4. `driver.c:181` accel switch → 同上

已知代价（方案 A 的取舍）：±2000 量程下 1 LSB = 0.061 dps，量化噪声比 ±250 差 8 倍，
修复后 yaw 可能比之前"看起来更抖"——这是正确缩放带来的真实噪声，不是新 bug。
若嫌抖，改方案 B（FS_SEL=1 → ±500 / 65.5，1 LSB = 0.0153 dps）即可。

`ATT_GYRO_DEADBAND_DPS` 仍是 0.20（未改）。修复后它是相对合理的值；
若仍发现慢转丢失，再降到 0.05。

### 这轮新挖出的关键事实（写文档时才发现，之前没记录）
1. **`unpack_task` 不是被中断叫醒的**：中断只置 `g_is_dma_readed`，由 prio3 的
   `mpuxxx_handler_thread` 每 1ms 轮询后 `queue_put` 投令牌。
2. **P0：令牌与槽位会永久失步**。`handler.c:326-339` 是「读标志 → queue_put → 清标志」，
   非原子。DMA ISR 若插在中间，会把下一包的标志一起清掉 → 丢 1 个令牌 →
   `wflag - rflag` 永久 +1 → 读指针落后 26ms。累积满 10 槽后开始读正在被 DMA 写的槽（撕裂帧）。
   窗口 ~1-2µs / 26ms ⇒ 期望 ~5-10 分钟命中一次。
   修法：临界区里原子取走标志（3 条指令），put 放临界区外。
3. **P0：DMA 启动失败会永久停摆**。`int_interrupt_callback` 先关 MPU 中断再启动 DMA，
   若 `iic_mem_read_dma` 返回 -2（`s_dma_busy`），中断保持关闭，数据流再也不来。
4. **INT 引脚从未配置**（`mpuxxx_set_INT_level` 只在未调用的 fifo_init/motion_init 里）→
   默认推挽高有效 50µs 脉冲、非锁存。EXTI 配的是**下降沿**，实际是在脉冲结束时触发
   （延迟 50µs，能用）。代价：空闲时推挽驱动低电平，40k 上拉持续灌 ~82µA。
5. **EXTI ISR 里做了 3 次阻塞 I2C**（关中断/读 INT_STATUS/启动 DMA）≈0.9~1.2ms，
   与 1ms SysTick 同量级，**可能吞 tick**（SysTick 优先级 15，抢不过优先级 5 的 EXTI）→
   dt 系统性偏小 → yaw 少转。**未实测，文档里标注为"必须实测确认"**。
6. 队列深度 20 > 缓冲 10，令牌容量形同虚设；`data` 令牌内容完全没用。
7. `circular_buf` 的 `data_writed/data_readed` 无满/空判断（代码里留 todo）；
   `buffer_init` 的 malloc 未判空。

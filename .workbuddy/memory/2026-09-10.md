## 深入答疑：PendSV / SysTick 优先级机制（已沉淀进指南文档）

用户追问两件事：`为什么 PendSV 最低` + `SysTick 也最低难道 tick 不会不准吗` + `最低优先级是硬件设计的吗`。
核实了 `OS/port/port.c` 源码后作答，并把结论补进 `docs/FreeRTOS_零基础循序渐进指南.md` 新增的 **§1.9**。

### 核实到的源码事实（重要，避免再次讲错）
- `OS/port/port.c:434-438` 官方注释原文：
  `/* Make PendSV and SysTick the lowest priority interrupts, and make SVCall the highest priority. */`
  → `SHPR3 |= PENDSV_PRI(0xFF<<16)`、`SHPR3 |= SYSTICK_PRI(0xFF<<24)`、`SHPR2 = 0`(SVC 最高)。
- `OS/port/port.c:67-69`：`portMIN_INTERRUPT_PRIORITY = 255UL`（**写死 255**），
  PendSV = `<<16`、SysTick = `<<24`。
  ⚠️ **这里没有用 `configKERNEL_INTERRUPT_PRIORITY`** —— 改 FreeRTOSConfig.h 配置项
  **不会**改变 PendSV/SysTick 的实际优先级。
- 寄存器：`SHPR3 = 0xE000ED20`（PendSV bit23-16、SysTick bit31-24）；`SHPR2 = 0xE000ED1C`（SVC bit31-24）。
- 写 0xFF 的技巧：STM32F4 只实现每字段高 4 位，0xFF 生效为 0xF0 → 优先级 15 = 最低；
  全写 1 可适配任意位数实现，移植层免条件判断。
- **复位值 SHPR3 = 0 → PendSV/SysTick 默认是最高优先级**，最低是软件（RTOS 移植层）主动改的，
  不是硬件固定。硬件提供的是「可挂起的系统异常 + SHPR 可配优先级 + 尾链」这套能力。

### 关键结论：SysTick 最低的代价（用户质疑是对的，之前表述不完整）
- tick 硬件计数器周期**永远准**（独立于 NVIC）；但 **ISR 执行会延迟**，进而 `xTickCount` 落后。
- 丢 tick 判定：任一 ISR / 关中断临界区连续占用 CPU **超过 1 个 tick 周期**
  （本工程 tick=1ms）→ pending 位是单 bit 不累加，**永久丢 tick**，所有延时超时被拉长。
- <1 tick 延迟：不丢，只是抖 ±1 tick（本来就有）。
- 设计取舍：外设 ISR 丢字节=硬错误 vs tick 晚 1ms=软降级 → 让路外设，代价由「ISR 必须短」兜。
- 需要精确时基时：别用 `xTaskGetTickCount()`；或覆写弱函数 `vPortSetupTimerInterrupt()`
  改用 TIM 做 tick 源并自行配 NVIC 优先级（PendSV 仍保持最低）。

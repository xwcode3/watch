## BSP 桥接驱动挂载函数命名约定（建议，待落地）

- 讨论：AHT21 桥接驱动新增中，是否应与已跑通的 LED 桥接驱动保持相同挂载函数命名风格。
- 结论：应统一。"桥接"的价值在于抽象层/调用方可互换实现，命名不统一就失去可替换性，也难做 code review。
- 现状是"半统一"：guard(`BSP_<模块>_H`)、`pf_` 前缀、实例类型 `bsp_<模块>_t` 已一致；
  不一致处：① LED 控制指针 `pf_led_countroler`（拼写错+带设备名词），AHT21 handler 改用 `temp_humi_xxx_*`
  与 driver 的 `aht21_*` 脱节；② 每个模块自创一套 status 枚举且 RESERVED 哨兵值不一（LED=0xFF / AHT21=0x7FFFFFFF）。
- 建议 house style：`ops` 结构体 `<module>_ops_t`，字段本模块方法 `pf_<verb>`、仅内嵌底层引擎才 `pf_<engine>_<verb>`(如 pf_iic_*)；
  返回值统一 `osal_status_t`/`bsp_status_t`（0=OK）；handler 词汇二选一（设备专属 aht21_* 或通用 temp_humi 子系统，但要去掉 xxx 占位并文档化）。
- 真 bug：AHT21 `pf_read_id` typedef 为 `(void* const)` 却挂 `aht21_read_id(uint8_t*)`，强转掩盖签名不匹配，调用处会传错参。

## handler 层选型确认：通用 temp_humi 子系统（可换芯）

- owner 决策：温湿度传感器可能更换（这次 aht21，下次可能是另一款温湿度 sensor），希望只改 driver 不动 handler。
- 这正是桥接模式的核心收益，确认走 R2(b)：handler 做成设备无关 `temp_humi` 子系统；driver 做设备专属 `<device>_*`。
- 落地要件：抽设备无关抽象接口 `temp_humi_ops_t`（`pf_init/pf_read_data/pf_read_id/pf_sleep/pf_wakeup`，不支持置 NULL），
  handler 用 `const temp_humi_ops_t *ops + void *dev` 接线，不持有具体 `bsp_aht21_driver_t*`。
- 当前 handler 仍直接持有 `bsp_aht21_driver_t*`，是耦合的，需先做这步解耦才真正"可换芯"。命名上删除 `xxx` 占位 → `bsp_temp_humi_handler_t`。
